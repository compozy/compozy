# BUG-0031: Memory health truncates workspace file totals at the prompt scan cap

## Summary

Memory health reported `workspace_files=200` for a workspace whose exact public catalog contained 206 valid Markdown headers. The health path reused `Store.Scan`, whose deliberate product contract caps prompt-oriented source discovery at 200. The cap is correct for prompt assembly but false for an operator-facing health total.

The indexed count remained 210 (4 global plus 206 workspace files), so the same health payload contradicted itself and could mislead an operator into diagnosing six indexed rows as stale or orphaned even though `orphaned_files=0`.

- **Charter:** CH-039 · **Tour:** Interrupt Tour
- **Environment:** isolated `northstar-pay-20260711-153916-425791` lab; registered workspace `ws_dc76b2b52e82493a`; 206 valid workspace memory files plus 4 global files.

1. Materialize more than 200 valid memory headers in one workspace.
2. Confirm the counted Memory catalog reports `total=206` for that workspace.
3. Read `GET /api/status?workspace_id=...`, `GET /api/memory/health?workspace_id=...`, or `agh__memory_health`.
4. Observe `workspace_files=200`, `indexed_files=210`, and `orphaned_files=0`.

**Expected:** Health counts every valid source header and agrees with the exact catalog and derived-index totals.
**Actual:** The source count stops at the prompt scan cap of 200.

## Fix

- **Root cause:** HTTP status/health, Settings, and the native Memory health tool counted the bounded `Store.Scan` slice instead of the uncapped physical source headers.
- **Fix:** Add `Store.SourceHeaderCount`, which reuses the uncapped physical header scan while preserving the 200-file `Store.Scan` contract. All three public health paths now use the same exact source counter. Catalog and orphan semantics remain separate.
- **Fix commit:** `f6748f2f`
- **Regression tests:** Canonical Store, core HTTP, Settings, and native-tool suites prove a source count above 200, exact global/workspace totals, and unchanged orphan behavior.
