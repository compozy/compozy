# BUG-0034: Recovering a task does not publish task.recovered to connected SSE subscribers

- **Status:** fixed
- **Impact (user-side):** Blocks-Completion
- **Severity:** High · **Priority:** P0
- **Persona Affected:** Operator
- **Journey Step:** TA-016 Task live SSE stream
- **Scenarios:** TA-016
- **Found:** 2026-07-11 · **Report:** docs/qa/reports/2026-07-11-goal-execution.md
- **Origin:** n/a

## Summary

Task recovery persisted the transactional `task.recovered` event correctly, but did not publish that committed record to already-connected live subscribers. The tab issuing Recover refreshed from its mutation response and appeared correct, while a second tab watching the same task kept the stale `needs_attention` badge until a reload or reconnect.

## Reproduction

- **Charter:** Task 08 browser E2E backbone · **Tour:** Network Tour
- **Environment:** current Goal worktree; isolated Playwright runtime.

1. Create a task and drive its recurrence breaker to `needs_attention`.
2. Open the task detail in two browser tabs and wait for both task SSE streams to connect.
3. Invoke Recover from the first tab.
4. Observe the badge in the second tab without issuing a mutation or reloading it.

**Expected:** The committed `task.recovered` frame reaches every connected subscriber and both tabs clear the `needs_attention` state live.  
**Actual:** The acting tab cleared through mutation-driven invalidation, but the observer tab remained stale because no live SSE frame was emitted.

## Evidence

- Browser reproduction and regression: `web/e2e/__tests__/tasks-hardening.spec.ts`, `task detail exposes the needs_attention badge and a Recover action that clears it live`.
- Owning service regression: `internal/task/manager_test.go`, `TestManagerRecoverTaskClearsEscalationAndAutoEnqueuesReadyTask/Should recover an escalated task and auto-enqueue when ready`.
- Initial failing gate: `make test-e2e-web` on 2026-07-11.
- Fresh post-fix gates: focused browser case passed; full `make test-e2e-web` passed all 62 cases; `go test -race ./internal/task/...` passed all 467 tests.

## Fix

- **Root cause:** `RecoverTask` used the store's atomic clear mutation, which co-committed `task.recovered`, but the store returned only the Task projection. The initial fix reconstructed candidate events from a separately sampled cursor and event type, which could not prove the identity of the event created by that transaction.
- **Fix commit:** pending operator commit.
- **Production fix:** `ClearTaskNeedsAttention` now returns `NeedsAttentionClearResult`, containing the updated Task and the exact `EventRecord` assembled inside and returned only after the same immediate transaction commits. `RecoverTask` publishes that one record directly to the domain observer and every live subscriber on a cancellation-detached post-commit context; the cursor/type reconstruction helper was deleted.
- **Regression tests:** the GlobalDB lifecycle suite compares the returned record with the persisted row field for field. The canonical Manager recovery suite installs a real `EventObserver`, opens two simultaneous subscribers, persists a neighboring same-type record, and proves every live recipient receives only the exact transactional identity. The existing browser task-hardening suite proves a non-acting observer tab updates only through SSE.
