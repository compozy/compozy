# BUG-0036: Browser Back bypassed the agent Settings unsaved-changes guard

- **Status:** fixed
- **Impact (user-side):** Data-Loss
- **Severity:** High · **Priority:** P1
- **Persona Affected:** Bruno; Sol
- **Journey Step:** J-31 edit Settings, then navigate Back before saving
- **Scenarios:** RT-078
- **Found:** 2026-07-11 · **Report:** `docs/qa/reports/2026-07-11-agent-details.md`

## Summary

An agent Settings draft correctly showed `Discard` and `Save changes`, but an in-app browser-history Back could leave the route without opening the custom unsaved-changes dialog. The draft was then lost.

## Reproduction

- **Charter:** CH-051
- **Environment:** fresh isolated lab `agent-details-task-09-20260711-190957-738761`

1. Open an agent detail page and use the in-app `Edit settings` action.
2. Change `Category path` and confirm the top bar exposes `Discard` and `Save changes`.
3. Trigger browser history Back.

**Expected:** `Discard unsaved changes?` blocks navigation and offers `Keep editing` or `Discard changes`.
**Actual:** The route could navigate back immediately and lose the draft.

## Fix

- **Root cause:** `useUnsavedGuard` passed a new inline `shouldBlockFn` to TanStack Router on every render. `useBlocker` registers its history blocker in an effect keyed by that callback; the resolver render therefore tore down and re-registered the blocker while navigation was pending.
- **Fix commit:** `f7d8a96`.
- **Production fix:** memoize the blocker predicate with `useCallback` for the lifetime of an unchanged dirty state.
- **Regression:** the canonical hook suite proves predicate identity remains stable across an unchanged dirty rerender; the existing browser Settings journey now invokes `window.history.back()`, keeps editing through the dialog, and verifies the draft remains.
