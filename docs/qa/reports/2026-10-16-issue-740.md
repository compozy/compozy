# Issue #740: provider-attributed catalog refresh failures

## Confirmed cause and change

The aggregate refresh can return source statuses with a non-success HTTP status
when a live source serves stale fallback. The Web adapter discarded those
statuses and the session composer rendered the raw error. Even successful
aggregate refreshes were reduced to the first failed source's diagnostic text.

The shared source projection now derives an optional `failure_reason` from its
persisted, redacted diagnostic: `auth_required`, `timeout`, or `refresh_failed`.
No database migration or change to refresh HTTP status semantics is needed.
Diagnostics stay in `last_error`; Web and human CLI status show guidance.
The selector renders an attributed provider notice and keeps model choices.

## Review remediation

CodeRabbit and Greptile identified request errors hidden by successful/disallowed
source rows or older failed statuses, and auth guidance retained in the browser's
one-time readiness cache. The selector now reads source health from the existing
aggregate status endpoint through a shared Query cache. Both aggregate and
provider refreshes invalidate that cache; readiness remains a boolean. A safe
request error is suppressed only when the current error supplies an attributed
failure that the page actually displays. Existing hook/settings suites cover
these paths, including recovery through the Settings mutation and reopening.
The CLI's existing API error decoder now retains classified source failures from
non-2xx refreshes too. Human errors include provider guidance; structured errors
retain the redacted payload and existing exit-code semantics. The existing client
suite covers decoding, guidance, diagnostics, redaction, and exit code.

The second Greptile pass identified overlapping OpenAPI response alternatives
and a rejected readiness refresh that skipped source-health invalidation.
Refresh error alternatives now use `anyOf`; other response unions keep their
existing semantics. The existing spec contract suite validates both generic and
source-bearing 500/503 payloads for both refresh routes. Readiness now invalidates
the catalog in `finally`, so an earlier empty status read is replaced immediately
after discovery fails. The existing hook suite passed all 14 tests, including
this ordering regression. Focused spec race tests and scoped spec lint passed;
React Doctor again reported no issues (93/100).

The test-shape helper reports a pre-existing direct-assertion function in
`spec_test.go` (`TestStopWhenSpecSchemaShouldMatchTheDualWireFormat`), outside the
modified catalog subtest. The new coverage stays in the canonical `Should...`
subtest; unrelated tests were preserved.

The final CodeRabbit pass found that a failed source-status reread can retain
older successful data. The selector now uses the refresh error's source rows
when that status read is in error. Successful authoritative reads still win, so
Settings recovery is not replaced by a retained mutation failure. The existing
hook suite covers the failed-reread ordering and healthy model availability.

A subsequent Greptile finding extended that sequence: after Settings recovery,
another failed status poll could revive the retained mutation error. Catalog API
errors now retain their client observation time. The hook permits their source
fallback only while no newer successful source-status read exists. The existing
ordering case now performs recovery and then another failed reread, verifying
that sign-in guidance stays cleared and healthy models remain available. The
adapter/hook suites passed all 25 cases. This timestamp is Web-internal metadata;
public payloads, status codes and persisted state are unchanged.
