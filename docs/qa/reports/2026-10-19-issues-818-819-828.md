## Desktop permission policy (#819)

An isolated Electron 44.5.1 process on macOS loaded the production
`applyDefaultDenyPermissions` module against two temporary loopback HTTP origins. Its user-data
directory was private to the QA lab. No host daemon, desktop configuration, or keyring was changed.

Observed results:

| Probe | Result |
| --- | --- |
| Product main-frame `Notification.permission` | `granted` |
| Product main-frame `Notification.requestPermission()` | `granted` |
| Same-origin iframe request | `denied` |
| Foreign-origin main-frame request | `denied` |
| Main-frame request without configured product origin | `denied` |
| Product geolocation permission | `denied` |
| Constructing a notification | No exception; no show event within five seconds |

The policy integration passed. OS notification display remains unverified: absence of a show
event is not evidence of delivery. Linux/KDE and Windows were not exercised. The complete
Settings/background-delivery journey in the packaged application is still pending.

The lab's targeted teardown reported `clean: true`; no lab process was retained. The initial
harness used top-level ESM await and stalled before Electron readiness. It was stopped through
its registered PID and corrected to asynchronous CommonJS startup before the observations above.
