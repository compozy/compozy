## Retained: task stream cross-query refetch amplification

`web/src/systems/tasks/lib/task-live-refresh-coordinator.ts` invalidates every run-detail and run-inspect query on each task's stream event. Both canonical responses include an immutable task ID. With many active task windows, a change to one task rereads unrelated run endpoints.

Test invariant: a task event refreshes that task's run detail/inspection, preserves unrelated populated run reads, and conservatively refreshes reads whose owner identity is not yet available. Owning layer: Tasks live-query coordination. Canonical suite: `web/src/systems/tasks/hooks/__tests__/use-task-stream.test.tsx`. Existing coalescing, cleanup, pagination, and stream lifecycle cases remain intact.

The coordinator now reads the immutable owner ID from populated canonical run-detail and run-inspect snapshots. Known unrelated owners are excluded; missing snapshots or missing owner IDs still receive a canonical reread. Agent-context and review query behavior stays unchanged because these query shapes do not supply an equally reliable task identity. No timer, persistent cache, new query key, or additional stream owner is introduced.

Five repetitions used 50 active TanStack QueryObserver pairs (run detail plus run inspection), with one stream refresh request for `task_0`. This measures endpoint reread amplification, not 50 rendered windows or user latency.

| Same fixture, Bun 1.4.4 | Before | After |
| --- | --- | --- |
| Run endpoint rereads per event, five samples | 100, 100, 100, 100, 100 | 2, 2, 2, 2, 2 |
| Median and range | 100 (100–100) | 2 (2–2) |

The reduction is 98%. Baseline deliberately ran the new behavioral assertion against unchanged production code: that assertion failed with the five 100-call samples while the other 18 cases passed. After the implementation, all 19 cases pass. Existing burst coalescing, cleanup, pagination, replay and stream lifecycle cases remain in that same suite.

## Concurrency decision

The session API enrichment paths already batch their I/O. Adding goroutines around shared payload decoration would add coordination and load to the same SQLite owners without a measured benefit. Tasks excludes irrelevant reads; the worktree service owner batches its remaining hydration after applying the API's selection. CLI/build/test-only packages do not justify increasing process concurrency under the user's machine-resource constraint.

### Static SDK findings retained for triage

- **SDK-A1 — omitted notes limit expands work to all retained notes.** At `sdk/examples/notes-commands/main.go:48–55`, `recent(0)` selects the entire store. The schema at line 72 makes `limit` optional and advertises default 5 / maximum 50, while the handler at lines 134–135 passes the decoded zero value directly. A raw `tools/call` with `input: {}` after 51 successful additions therefore returns 51 notes, cloning and rendering O(history) data instead of the advertised default-sized result. `sdk/go/extension.go:183–188` performs ordinary zero-value JSON decoding; `internal/tools/schema.go` validates without injecting defaults. The existing CLI test “Should pass raw JSON through canonical parsing without injecting defaults” confirms that raw command input intentionally retains this distinction. This is an example-level pre-existing behavior, not a regression introduced by the performance patch. No runtime reproduction or optimization measurement was performed; any fix should apply the example's explicit default at its owning handler and verify tool/command parity before retention.
- **SDK-A2 — stdio cancellation begins after synchronous output admission.** `sdk/go/transport.go:197` calls `writeFrame` before reaching the context select at line 202. `writeFrame` at lines 400–413 waits on the shared write mutex and the arbitrary `io.Writer`; cancellation cannot interrupt a peer that stops consuming output at this point. `transport_inbound.go:25–36` additionally admits one goroutine per inbound request, so the per-frame cap is not an aggregate in-flight cap. These are concrete static backpressure limits, not evidence that normal daemon traffic currently saturates the SDK. Existing cancellation coverage begins after the initial request has been consumed. No concurrency limit or detached-writer workaround was introduced: bidirectional callbacks require the reader to remain able to deliver responses, and arbitrary reader/writer ownership must be preserved. A future measured change needs a stalled-peer fixture and explicit lifecycle/admission semantics in the existing transport suite.

The supplemental pass retains no SDK optimization. It adds source-level coverage and identifies the two boundedness follow-ups above without promoting static reasoning, existing CI runs, or unrelated API measurements into SDK runtime evidence.
