# QA bootstrap provider isolation (#1148)

Scope: bootstrap tooling and its provider resource lifecycle. No daemon, UI,
credential rotation, or operator configuration changes.

## Real validation (macOS, installed daemon 0.4.8)

- Created a fresh targeted API lab without the provider surface. Before startup,
  the isolated Codex home had no `auth.json` or global skills/cache links and the
  runtime config disabled provider usage.
- Started the real daemon against the manifest's isolated home, port and socket,
  registered its process identity, then inspected its two runtime logs: zero
  lines containing `provider_usage`, including after teardown.
- Ran the manifest teardown: `clean: true`, no survivors and no provider resource
  errors. Only this lab's processes were targeted.
- Created a separate targeted provider lab. Under its isolated HOME/CODEX_HOME,
  `codex login status` exited 0 with `Logged in using ChatGPT`. No model turn or
  account usage collection was requested. Credential contents were never displayed.
- Teardown reported `clean: true` and removal of all three allowed provider files
  plus both global skills/cache links. The operator originals were untouched.

The installed host passed an internal restart operation ID to native terminals;
the isolated daemon launch cleared that variable only for its child process.
Mise shims under a swapped HOME refused untrusted configuration, so the login
status check used the installed CLI with the installed Node directory on PATH.
No trust settings were modified.

## Focused checks

The existing `bootstrap-qa-env-smoke-test.py` suite owns bootstrap integration,
provider opt-in, legacy reuse cleanup, usage opt-in persistence, teardown dry-run,
bare-root stale recovery, blocking resource removal failures, and process identity
isolation. It runs with a short canonical temp root on macOS.

Heavy gates and full E2E are delegated to PR CI per the issue assignment. This
report does not claim a full provider-usage UI walk or a live model turn.
