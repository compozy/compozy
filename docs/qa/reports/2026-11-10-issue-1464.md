# Issue #1464 validation

## Confirmed cause and implementation

The browser serialized session mutations in `runSessionBatch` and worktree cleanup in
`useWorktreeRemovalBatch`. The daemon already serializes SQLite writes and Git mutations by
canonical repository. The browser now uses the existing `settleBounded` worker helper with
a limit of three. Session targets sharing the daemon's lineage root stay sequential, including
forks, continued sessions and selected descendants covered by a root operation.

Row and selection menus share action metadata. Selection adds Mark as seen, Make top-level and
Copy titles; owner-scoped singular endpoints remain authoritative. Successful receipts survive
retries and each failure names its target. No public route, DTO, state migration or config change.

## Real isolated-daemon timings

The current checkout was built into a temporary daemon binary. All requests targeted a fresh
lab with its own home, HTTP port and Unix socket. No provider turn, mock response, user's daemon
restart or installed-runtime update was involved. Each selection contained 15 independent
unbound sessions or 10 real Git worktrees adopted through the public API. The scripts compare
sequential HTTP requests with a pool of three against the same unchanged daemon endpoints.
These are public API timings, not browser rendering or live-agent stop latency.

a cause for the slow initial sample. Initial Vite compilation and focused checks shared the host.
No claim is made that every batch finishes in the time of its slowest member: a limit of three
requires several waves, and Git mutations within one repository deliberately remain serialized.
