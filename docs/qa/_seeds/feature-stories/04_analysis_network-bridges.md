## Overview

This slice covers the **AGH Network** runtime (channels, threads, direct rooms, peers/presence, work items, send/inbox, network status & settings), the **Bridges** subsystem (external messaging adapters: instances, providers, lifecycle, routes, targets, secret bindings, delivery test, health), **task-scoped bridge notification subscriptions**, and **notification presets**. All three subsystems share one architectural pattern: handlers live once in `internal/api/core` as `BaseHandlers` methods and are registered identically by the HTTP (`internal/api/httpapi/routes.go`) and UDS (`internal/api/udsapi/routes.go`) transports, then consumed by both the React SPA (`web/src/systems/{network,bridges,notifications}`) and the Cobra CLI (`internal/cli/{network,bridge,notifications}.go`). Most surfaces are therefore triple-exposed (HTTP + UDS/CLI + web), satisfying the "agent-manageable by default" rule — with several exceptions captured under Risks.

The Network surface is the largest. Channels are not lightweight rooms: creating a channel **spawns one daemon session per selected agent** (`CreateNetworkChannel`, `network_details.go:82-158`) and rolls those sessions back on any persistence failure. Conversation surfaces are `thread` and `direct`; the public channel timeline, threads, and directs are read-only projections built by merging live peers, persisted sessions, and persisted messages. Sending is a single validated endpoint (`NetworkSend`) that fans into kinds `greet | whois | say | capability | receipt | trace` with strict field-scope rules (greet/whois carry no conversation fields; say/capability/etc require a `surface`; capability/receipt/trace require `work_id`). The web UI only ever sends `kind="say"` into `thread`/`direct` surfaces (`use-network-actions.ts:57,81`), so the richer kinds are agent/CLI/API-only.

Bridges are CRUD + lifecycle (`disabled → starting → ready`, plus `degraded | auth_required | error`, `internal/bridges/types.go:126-137`) with secret-binding management, friendly-target resolution, and a "test delivery" dry-run that resolves an outbound target without a live platform adapter. Bridge **health** is the only SSE stream in this slice (`StreamBridgeHealth`); the network surfaces are poll-driven on the web (`query-options.ts` `refetchInterval`).

The operator is most likely to act on: (1) the network channel/thread/direct/peer browsing and message-send flows (the visible web product), (2) bridge create→enable→test-delivery lifecycle, (3) two orphaned message-timeline handlers that exist in core but are wired into no route, and (4) the truthfulness gap between "live message flow" copy and poll-based refresh. These are the highest-value QA and UX targets.

## Mechanisms / Patterns

- **Single-home handlers, dual transport:** Every network/bridge/notification endpoint is a `BaseHandlers` method registered identically in HTTP and UDS route files (`httpapi/routes.go:68-95,399-418`; `udsapi/routes.go:60-89,423-444`). QA can exercise the same behavior via REST and via CLI/UDS.
- **Network workspace scoping:** All channel/peer/thread/direct/work/send/inbox routes are nested under `/workspaces/:workspace_id/network/...`; `NetworkStatus` is the only global network route (`/api/network/status`). Scope mismatch between path and body `workspace_id` is a 400 (`network.go:169-176`).
- **Channel creation spawns sessions:** `CreateNetworkChannel` validates channel name + non-empty `purpose` + non-empty, de-duplicated `agent_names` that must all be available in the workspace, then `createNetworkChannelSessions` starts one `SessionTypeUser` session per agent and rolls them back on failure (`network_details.go:82-158,733-759`).
- **Read-only timeline projection:** Channel detail/list counts merge live peers + persisted sessions + persisted messages into aggregates, with presence (`greet`) messages collapsed into windowed episodes (`network_details.go:535-690,1283-1328,1427-1489`).
- **Conversation surfaces are isolated:** Threads and directs each have list, detail, and `/messages` endpoints; direct rooms are resolved deterministically via `DirectRoomIdentity(workspace, channel, localPeer, remotePeer)` from a caller session + target peer (`network_conversations.go:131-207`).
- **Strict send validation + token redaction:** `NetworkSendRequestFromPayload` enforces required fields, valid JSON body, kind-scope rules, and rejects raw `claim_token` fields (`network.go:284-415`). Same validation is mirrored in the CLI (`cli/network.go:1502-1576`).
- **Peer presence + capability cards:** `ListPeers` returns peer cards (display name, capability brief, profiles, artifacts, trust modes) and presence state `local|active|inactive|expired|unknown` with `last_seen_age_seconds`; peer detail adds a capability catalog and sent/received/rejected/delivered metrics derived from the audit log (`network.go:46-74,492-535`; `network_details.go:347-400,1675-1718`).
- **Work items:** `GET /work/:work_id` returns a work row with state `submitted|working|needs_input|completed|failed|canceled` (`envelope.go:165-170`; `network_conversations.go:263-283`).
- **Bridge lifecycle as transitions:** enable/disable/restart funnel through `transitionBridge` → Start/Stop/Restart instance, returning instance + enriched health (`bridges.go:333-346,839-893`).
- **Bridge diagnostics enrichment:** list/get responses enrich health with provider-catalog-aware diagnostics and secret-binding checks (`bridge_diagnostics.go:17-150`).
- **Bridge target resolution diagnostics:** `ResolveBridgeTarget` returns 422 (`CodeTargetAmbiguous`, with candidate count) or 404 (`CodeTargetUnknown`) carrying a structured diagnostic (`bridges.go:453-555`).
- **Bridge health SSE:** `StreamBridgeHealth` prepares SSE, emits an initial snapshot, then diffs poll snapshots and emits only on change (`bridges.go:348-411`).
- **Task→bridge notification subscriptions:** task-scoped terminal notification targets validated against the task's scope/workspace and the bridge instance scope, with a delivery cursor surfaced in the payload (`bridges.go:655-1076`).
- **Notification presets CRUD:** list (filter by enabled/built_in/name/limit) + get/create/update/delete, surfaced in the web under **Settings → Hooks & Extensions** (`notifications.go:17-160`; `settings/hooks-extensions.tsx:27,197`).
- **Web is poll-driven for network:** network queries use `refetchInterval` + `refetchOnWindowFocus` (`query-options.ts:48-104`); there is **no** network SSE handler (bridge health is the only stream).

## Transferable Patterns

- {Single-home handler + dual transport} → applies to the spreadsheet's "Entry points" column because every story can list HTTP + UDS/CLI together; the parent can test the same invariant through REST and CLI.
- {Strict kind-scope validation on send} → applies to QA charters for NB-020 because each kind has distinct required/forbidden fields; the parent can derive a table of valid/invalid send payloads directly from `network.go:351-415`.
- {Deterministic direct-room identity} → applies to NB-014 reproducibility because resolving the same pair twice must return the same `direct_id` (idempotency check).
- {Diagnostic-bearing error responses (422 ambiguous / 404 unknown)} → applies to NB-035 negative-path testing because the structured diagnostic + candidate count is observable, not just a status code.
- {SSE diff-on-change} → applies to NB-032 because the stream should stay silent when health is unchanged and emit on transition; a good automated assertion target.
- {Poll-driven web with `refetchInterval`} → applies to all network web stories' QA notes because "did it update?" depends on the poll cycle, not push; tests must wait for refresh.

## Risks / Mismatches

- **Orphaned message-timeline handlers (transport dead code).** `BaseHandlers.NetworkChannelMessages` and `BaseHandlers.NetworkPeerMessages` are fully implemented (`network_details.go:191-345`) and return real responses (`NetworkChannelMessagesResponse`, `NetworkPeerMessagesResponse`), but **no route registers them** in either `httpapi/routes.go` or `udsapi/routes.go` (the only routed `/messages` endpoints are thread- and direct-scoped). Only thread/direct/peer-detail timelines are reachable. This conflicts with the "no partial-surface completions / agent-manageable by default" rules. The `h.NetworkChannelMessages(...)` calls in `internal/testutil/e2e/runtime_harness.go:1250,1303` are a different harness client method, not these gin handlers. → Parent should decide: wire them or delete them. *(Evidence: grep found references only in core definitions + contract + tests.)*
- **"Live message flow" copy vs poll-based refresh.** `settings/network.tsx:153` advertises "live message flow", and the network surfaces refresh via `refetchInterval` (`query-options.ts:48-104`); there is **no** network SSE handler (only `StreamBridgeHealth`). This risks a truthful-UI mismatch (`DESIGN.md`/`COPY.md` "truthful UI > plausible UI"). → Capture as a UX/logistics risk; verify whether "live" overstates the mechanism.
- **Notification preset update has no CLI verb.** API + web support `PUT` update (`notifications.go:86-111`), but the CLI only registers `show/create/delete` (`cli/notifications.go:90,115,200`) — no `notification update`. Partial agent-manageable surface (update is web/API only). → NB-046 marked `Potential UX/logistics risk`.
- **Web send is a strict subset of the send contract.** The web composer only emits `kind="say"` into `thread`/`direct` surfaces (`use-network-actions.ts:57,81`). Public-channel `say` and kinds `greet|whois|capability|receipt|trace` are agent/CLI/API-only. Not a bug, but the spreadsheet must not imply the web exposes the full send grammar.
- **Slice overlap — network settings (NB-002).** `settings/network.tsx` + `GET/PATCH /api/settings/network` likely also fall under a settings-focused slice (03). → Keep NB-002 here for completeness but flag to the parent to de-duplicate during synthesis.
- **Slice overlap — task bridge notifications (NB-040..043).** These live under `/api/tasks/:id/...` and may also appear in a tasks/autonomy slice. → Flagged for synthesis-time de-duplication; they are included here because the behavior is bridge/notification semantics.
- **Peer detail CLI exposure uncertain.** `NetworkPeer` (`/peers/:peer_id`) is HTTP/UDS-routed, but I did not confirm a CLI verb for single-peer detail (CLI `network peers [channel]` lists). → Open Question.
