## Overview

This slice is the operational heart of AGH's autonomy kernel as exposed to users and agents. It spans four cooperating subsystems. **Tasks** (`internal/task`) own durable task records and the authoritative `task_runs` queue with `ClaimNextRun` as the single claim primitive. **Automation** (`internal/automation`) owns cron/interval scheduled jobs, event/webhook triggers, and a durable scheduler-state store. The **mechanical scheduler** (`internal/scheduler`) is intentionally narrow — it sweeps expired leases, wakes idle sessions, and emits wake notifications but never claims runs itself (`internal/scheduler/doc.go`). **Observe** (`internal/observe`) projects the task dashboard and inbox aggregates consumed by the web UI.

Every capability is exposed with HTTP↔UDS parity (`internal/api/httpapi/routes.go:243-336` ≈ `internal/api/udsapi/routes.go:254-355`), a CLI verb (`internal/cli/{task,automation,scheduler}.go`), and — for the most common surfaces — a web route. The web app renders five task surfaces (List, Kanban, Dashboard, Inbox via `PillGroup` mode pills in `web/src/routes/_app/-tasks-route.tsx:38-50`), a task detail page with seven tabs (`web/src/routes/_app/tasks.$id.tsx:74-87`), a run-detail page (`web/src/routes/_app/tasks.$id.runs.$runId.tsx`), and a shared Jobs/Triggers operations page (`web/src/routes/_app/{jobs,triggers}.tsx` → `automation-operations-page.tsx`). Scheduler controls (pause/resume/drain) live inside the task **Dashboard** view rather than a dedicated route.

The operator is most likely to act on: (1) creating/running tasks and watching runs live via SSE; (2) the inbox/approval flow for human-in-the-loop tasks; (3) operator run-recovery actions (force-release, force-fail, retry, recover, bulk); (4) scheduler pause/drain during incidents; and (5) configuring automation jobs (cron/interval) and triggers (events/webhooks) including HMAC-signed webhook delivery.

This slice overlaps adjacent slices at well-defined seams: task runs attach **sessions** and the agent-claim flow validates session identity (sessions are another slice's domain); task runs reference **coordination/network channels** (network slice); task notifications fan out through **bridges** (bridges slice); and automation triggers fire on `session.created`/`session.stopped` events (session lifecycle slice). I capture the task/automation-facing surface and flag the seams in **Risks / Mismatches** rather than duplicating those stories.

## Mechanisms / Patterns

- **BaseHandlers shared-core pattern:** Every task/automation/scheduler endpoint is a `BaseHandlers` method in `internal/api/core/`, registered identically by HTTP and UDS routers. Transport only chooses registration + auth (`internal/CLAUDE.md` "canonical handler home"). Implication for QA: testing one transport validates handler logic; both transports must be smoke-checked for parity.
- **Actor-context resolution per action:** `taskActorContext` derives a human actor for HTTP/UDS/CLI/web, or resolves an agent caller from `AGH_SESSION_ID`/`AGH_AGENT` credentials (`internal/api/core/tasks.go:102-146`). Origin kind is inferred from transport name.
- **Draft lifecycle + list compensation:** Tasks can be created as drafts (`Draft: req.Draft`) and `PublishTask` promotes a draft into the runnable lifecycle (`tasks.go:484-526`). List endpoints hide drafts by default and over-fetch to compensate for client-side draft filtering (`listTasksWithDraftCompensation`, `tasks.go:1684-1731`).
- **Queue-first run lifecycle:** A run moves enqueue → claim → start → complete/fail/cancel. Manual lifecycle endpoints exist (`/task-runs/:id/{claim,start,attach-session,complete,fail,cancel}`) alongside the agent-authoritative lease path. Idempotency keys are accepted on enqueue/claim/start (`enqueueTaskRunFromRequest` etc., `tasks.go:1880-1926`).
- **Operator run recovery surface:** `/runs/:id/{release,fail,retry,recover}` and `/runs/bulk/{release,fail}` force-mutate runs without a claim token, gated by actor authority (`tasks.go:1357-1553`). `recover` terminalizes a `needs_attention` run and queues a fresh child run to resume work (`tasks.go:1471-1507`).
- **Agent autonomy claim primitive:** `AgentTaskClaimNext` is the only path agents use to acquire work. It supports long-poll `wait` (returns 204 when empty, or blocks then re-polls), capability + priority + workspace criteria, and a per-session "soul claim lock" to serialize claims (`agent_tasks.go:31-111`, `agentTaskClaimCriteria` 333-381). Lease heartbeat/complete/fail/release verify the claim token via `LookupActiveRunForSession` (`agent_tasks.go:145-331`). Claim tokens are redacted to `claim_token_hash` in all payloads (`AgentTaskLeasePayloadFromRun`, 474-498).
- **Task-run reviews with circuit breaker:** `RequestTaskRunReview` is idempotent/replayable (returns 200 existing or 201 created); verdict submission can open a circuit breaker and spawn a continuation run (`task_reviews.go:14-66,133-175`, `TaskRunReviewVerdictResponseFromResult` 268-281).
- **Triage + approval inbox:** Tasks carry an `ApprovalPolicy`/`ApprovalState`; approval-gated tasks expose `approve`/`reject`, and every task has per-actor triage state (`read`/`archive`/`dismiss`) surfaced by the observer inbox with unread counts and lanes (`tasks.go:1001-1091`, `internal/observe/tasks.go:493-496,931-992`).
- **Scheduler control plane:** `GetScheduler` returns pause state + queue pressure (active claims, queued, paused tasks, starved, needs-attention); `pause`/`resume`/`drain`/`backlog` are transactional through the task service (`scheduler.go:89-289`). Drain waits for active claims with a configurable timeout. Task-level `pause`/`resume` make runs claim-ineligible (`scheduler.go:13-87`).
- **Automation job scheduling modes:** Jobs support `cron` and `every` (Go duration interval) schedule modes plus catch-up policy (`internal/automation/types.go:34-74`, `schedule.go:505-516,888-909`). Web exposes a cron-builder, interval, schedule-at, retry policy, and fire-limit forms (`web/src/systems/automation/components/job-form/`).
- **Automation triggers — events + webhooks:** Triggers fire on `session.created`, `session.stopped`, or `webhook` events with optional filters (`internal/automation/trigger.go:25-79`). Webhook triggers carry a write-only HMAC secret + endpoint slug (`automation.go:999-1016`).
- **Webhook delivery security:** `POST /webhooks/global/:endpoint` and `/webhooks/workspaces/:workspace_id/:endpoint` require `X-AGH-Webhook-Timestamp`, `X-AGH-Webhook-Signature` (HMAC sha256), and `X-AGH-Webhook-Delivery-ID`, enforce a 1 MiB body cap, a freshness window, and per-delivery-ID replay rejection (`automation.go:21-33,492-520,695-769`; errors in `trigger.go:58-74`).
- **Config-backed vs dynamic source policy:** Jobs/triggers sourced from `config.toml` (`JobSourceConfig`) accept **only** `enabled` updates and cannot be deleted; dynamic ones are fully mutable (`automation.go:166-224,378-425,869-885,1023-1042`).
- **Source enrichment with scheduler state:** Job list/get/create/update responses enrich each job with next-run time + scheduler state, best-effort on mutations (`automation.go:534-592`).
- **Observe-backed empty/error/loading states:** Web surfaces all handle loading/error/empty explicitly (e.g. dashboard/inbox loaders, automation runtime-unavailable alert `automation-operations-page.tsx:70-112`, task detail not-found `tasks.$id.tsx:47-69`).

## Transferable Patterns

- **Spreadsheet status column → CLI/API/web entry-point trio.** Every story above resolves to (web route?, HTTP path, UDS path, CLI verb). The parent can fill a single canonical `Entry points` column from the route+CLI evidence and immediately know which surface to test first.
- **HTTP↔UDS parity is the cheapest correctness gate.** Because handlers are shared `BaseHandlers` methods, the parent's QA loop can assert that any task/automation story behaves identically over `:2123` HTTP and the CLI's UDS socket; a divergence is a real bug, not a feature gap.
- **Agent-manageable surface checklist.** Each capability exposes `-o json`-capable CLI verbs and HTTP/UDS parity, satisfying the "agent-manageable by default" invariant — the parent can route every story's QA through both a human (web) and an agent (CLI/API) actor.
- **Lease + token redaction as a security assertion.** TA-049…TA-051 give the parent a concrete redaction test: claim responses must expose only `claim_token_hash`, never `agh_claim_*`. This maps to the repo-wide security invariant and is a high-value bug-hunt target.
- **Config-source immutability (TA-061) as a negative-test template.** A clean, deterministic 400-path that the parent can reuse as a model for other "restricted mutation" stories.

## Risks / Mismatches

- **Webhook QA needs out-of-band signing (TA-060).** Delivery requires a valid HMAC sha256 over the body with a fresh timestamp and unique delivery-id. The parent cannot exercise this with a plain `curl` unless it computes the signature from the stored secret; marked `Blocked by uncertainty`. The signing recipe/secret resolution (`vault:` / `env:` refs) is not fully traced in this slice.
- **Scheduler has no dedicated web route.** Scheduler pause/resume/drain/backlog are only reachable in the UI through the task **Dashboard** view (`-tasks-route.tsx:76-93`), not a standalone page. A QA charter that looks for a "Scheduler" nav item will find none; the controls are dashboard-embedded. Not a bug, but a discovery risk.
- **Settings automation PATCH privilege asymmetry.** HTTP `PATCH /settings/automation` is wrapped with `privileged` middleware (`httpapi:461`) while the UDS route is not (`uds:490`). This is expected (UDS is local-trust) but the parent should verify the HTTP privilege gate actually rejects unprivileged callers.
- **Overlap with adjacent slices — do not double-count:**
  - **Sessions/ACP slice:** TA-026 (attach session) and TA-049…TA-051 (agent claim/lease) depend on session identity + lifecycle. I cover the task-run side; session creation/state machine belongs to the sessions slice.
  - **Network slice:** task runs/claims carry coordination/network channels (`agent_tasks.go:500-530`); channel management itself is out of scope here.
  - **Bridges slice:** TA-021 task bridge subscriptions reference the bridges subsystem; I capture only the task-scoped subscription endpoints.
  - **Session-event triggers (TA-057):** `session.created`/`session.stopped` events originate in the session lifecycle slice; I capture the trigger-consumer side.
- **`start` vs `enqueue` vs `publish` semantics overlap (TA-006/007/008).** Three near-adjacent ways to produce a run. The parent should confirm the precise distinction during QA (publish promotes a draft; start enqueues for an existing task; enqueue is the queue-first primitive) to avoid filing duplicate "run created twice" bugs.
- **Two manual run-lifecycle paths coexist** (operator `/task-runs/*` claim/start/complete vs agent lease `/agent/tasks/*`). Mixing them on the same run could race; a QA scenario that claims via operator API then completes via agent lease (or vice-versa) is a meaningful edge case.
