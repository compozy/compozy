## Overview

This slice owns AGH's **extensibility and tooling control plane**: the surfaces through which an operator (web UI) or an agent (native `agh__*` tools / CLI / HTTP / UDS) discovers, installs, configures, enables, and audits the runtime's pluggable capabilities. Eight cooperating sub-domains live here: **skills** (markdown capability packs with a five-layer precedence model and a remote marketplace), **extensions** (daemon-managed plugins with provenance/trust reporting), **bundles** (extension-shipped activation profiles that project agents/jobs/triggers/bridges/channels), **resources** (a generic desired-state CRUD control plane with optimistic concurrency and codec validation), **hooks** (a typed lifecycle dispatch taxonomy of ~70 events plus config-backed hook declarations), **MCP** (settings-configured MCP servers, OAuth/PKCE auth login, and an internal hosted-MCP bind/projection bridge for ACP agents), **tools** (the unified tool registry exposing operator and session projections, toolsets, approvals, and invocation), and the **native agent toolset** (`agh__*` IDs) that makes every one of these manageable by agents without the web UI.

The dominant architectural fact for testing is **surface parity**: nearly every capability is exposed through three transports — HTTP (`/api/*` for the web app), UDS (`/api/*` for the CLI), and native `agh__*` tools (for in-session agents) — all routed through one shared `BaseHandlers` set in `internal/api/core`. HTTP and UDS register the *same* handler methods (`internal/api/httpapi/routes.go` vs `internal/api/udsapi/routes.go`), differing only in privilege middleware and a UDS-only hosted-MCP group. This means a single user story frequently has three concrete entry points, and a known UX risk (surfaced by the web itself) is that **mutating settings/extension operations return HTTP 403 when the daemon is bound off-loopback**, falling back to UDS/CLI only.

The operator is most likely to act on: (1) the **Skills page** (`/skills`) — installed list with content viewer, shadow/precedence inspector, enable/disable toggles, and a marketplace tab; (2) the **Skills settings** page — disabled-skill tombstones (global + per-agent scope), registry policy, and marketplace allowlists; (3) the **Hooks & extensions settings** page — lifecycle-hook toggles, installed-extension lifecycle (toggle/update/remove/provenance), extension marketplace search/install with trust gating, and extensions resource policy; and (4) the agent-facing native tools that mirror all of the above.

This slice deliberately **excludes** (owned by adjacent slices): provider/model management, sandbox profiles, automation jobs/triggers, bridges as messaging adapters, AGH Network channels/peers, memory, sessions, and task-run orchestration — even though several of these appear as *referenced* fields here (bundle profiles enumerate bridges/jobs/triggers/channels; hooks fire on automation/network/task events; tools route to MCP/extension backends). Where a referenced surface is the primary subject of another slice, it is noted in **Risks / Mismatches** rather than given its own ET story.

## Mechanisms / Patterns

- **Shared-handler tri-transport parity:** every endpoint is a `BaseHandlers` method registered identically by HTTP and UDS (`internal/api/httpapi/routes.go:339-444` vs `internal/api/udsapi/routes.go:359-473`). HTTP wraps mutating routes in `privileged` middleware; UDS does not. Test implication: the same story must be verified on both transports, and HTTP-403/off-loopback behavior is a first-class case.
- **Skill scope resolution (global / workspace / agent):** `resolveSkillScope` reads `?workspace=` and `?for_agent=` query params; `List` → `ForWorkspace` → `ForAgent` projection chain (`internal/api/core/skills.go:415-459`). Enable/disable diverges: agent scope calls `SetEnabledForAgent` (logical tombstone), global calls `SetEnabled` (`skills.go:135-246`).
- **Skill content verification on read:** `GetSkillContent` calls `SkillsRegistry.LoadContent` (`skills.go:71-100`); per `internal/CLAUDE.md` security invariant, every non-bundled skill is re-scanned via `VerifyContent` on every load, not just install.
- **Skill shadow/precedence audit:** `GetSkillShadows` → `skills.ShadowsForSkill` returns every declaration that participated in resolving one logical skill name (`skills.go:103-132`), exposing the five-layer Bundled→Marketplace→User→Additional→Workspace precedence as a user-visible trail.
- **Skill marketplace lifecycle with post-mutation re-verification:** search/info/install/update(check|apply)/remove via `skillMarketplaceService()` (`skills.go:248-383`); after install/update/remove the handler calls `refreshSkillsAfterMarketplaceMutation` and `VerifyInstallVisible` to prove the installed skill is actually discoverable (`skills.go:299-328`) — a deliberate "truthful UI" guard worth testing for the failure path.
- **Extension install dual-mode + checksum gate:** `InstallExtension` accepts either a local `path` (requires `checksum`) or a marketplace `slug` (mutually exclusive), validated before dispatch (`internal/api/core/extensions.go:93-128`). Trust errors map to specific HTTP codes via `ExtensionStatusCode` (`extensions.go:214-240`).
- **Extension provenance/trust report:** `ExtensionProvenance` returns persisted `installed_from / registry_tier / checksum_sha256 / checksum_verified / allow_unverified / trust.decision` (`extensions.go:199-212`; rendered at `hooks-extensions.tsx:664-731`).
- **Extension actor-context derivation:** mutating extension ops resolve a `taskpkg.ActorContext` (`extensions.go:297-326`) — human (transport-derived) vs agent-caller identity — so the audit ledger records who installed/enabled/removed.
- **Bundle catalog → preview → activate lifecycle:** `ListBundleCatalog` enumerates extension-shipped bundles/profiles with agent/job/trigger/bridge counts (`internal/api/core/bundles.go:18-29,197-221`); `PreviewBundleActivation` (dry-run) and `ActivateBundle` materialize a profile into a scoped activation with inventory of projected resources (`bundles.go:31-74`, payload builder `223-301`). Extensions that declare a Live Network requirement need explicit confirmation of the current digest; Delete deactivates.
- **Bundle Network inventory:** `BundleNetworkSettings` reports declared channels only (`bundles.go:123-141`). Channel declarations do not select participation for any execution.
- **Resources generic desired-state CRUD with optimistic concurrency:** `ListResources` (filter by kind/scope/owner/source), `GetResource`, `PutResource` (codec validation via `ValidateAndCanonicalizeIfRegistered`, `expected_version` → 201 when 0 else 200), `DeleteResource` (requires positive `expected_version`) (`internal/api/core/resources.go:140-264`). Write triggers reconciliation (`resources.go:115-119`).
- **Tool registry dual projection + diagnostics:** `ListTools`/`SearchTools`/`GetTool` use an operator scope (`operatorToolScope`, `Operator:true`) while `ListSessionTools`/`SearchSessionTools` are anchored to a resolved route workspace+session (`internal/api/core/tools.go:21-233`). Each `ToolView` carries `Descriptor` (schema digests, risk flags, read-only/destructive/open-world), `Availability` (registered/enabled/available/authorized/executable/conflicted + reason codes), and `Decision` (policy outcomes per layer) (`tools.go:268-393`).
- **Tool approval + invoke flow:** `CreateToolApproval` mints a daemon-memory approval token bound to tool-id + input digest + scope (`tools.go:76-125`); `InvokeTool` dispatches with optional `ApprovalToken`, returning result/truncation/duration (`tools.go:128-176`). Stable client-safe error contract via `respondToolError` masks backend text (`tools.go:486-519`).
- **Toolsets with expansion diagnostics:** `ListToolsets`/`GetToolset` expand named sets to concrete tool IDs and report `expanded`/`degraded` status with reason codes (`tools.go:236-309`).
- **Hooks observability surface:** `HookCatalog` (observed hook entries, workspace-filterable), `HookEvents` (supported taxonomy), `HookRuns` (per-session audit, requires `session` query + workspace membership) (`internal/api/core/handlers.go:1432-1507`). Taxonomy is ~70 typed events across session/sandbox/input/prompt/event/automation/agent/turn/message/tool/permission/context/coordinator/task-run/spawn/network domains (`internal/hooks/events.go:56-142`).
- **Hooks settings as a config collection:** `ListSettingsHooks` / `PutSettingsHook` / `DeleteSettingsHook` (`internal/api/core/settings.go:292-313`) manage config-backed hook declarations; `GetSettingsHooksExtensions` / `UpdateSettingsHooksExtensions` manage the policy section + per-hook enable toggle (`settings.go:176-205`).
- **MCP server settings collection:** `ListSettingsMCPServers` / `PutSettingsMCPServer` / `DeleteSettingsMCPServer` (`settings.go:237-257`) manage MCP server config entries.
- **MCP OAuth/PKCE auth flow:** `Service.BeginLogin` (discovers metadata, requires S256 PKCE, returns auth URL + state+verifier), `Exchange` (callback→token), `Refresh`, `Status`, `Logout` (`internal/mcp/auth/service.go:90-217`). Surfaced to agents via `agh__mcp_auth_login` / `agh__mcp_auth_logout` / `agh__mcp_auth_status`.
- **Hosted-MCP internal bridge (UDS-only, agent-facing):** `/api/internal/hosted-mcp/{bind,projection,projection/stream,tools/call,release}` lets an ACP agent peer bind to a daemon-hosted MCP projection and call tools through the daemon, with peer-identity gating (`internal/api/udsapi/hosted_mcp.go:16-150`). SSE stream variant for live projection.
- **Native agent toolset (`agh__*`):** the entire slice is agent-manageable. Confirmed IDs: skills (`agh__skill_list/search/view/install/update/remove`), tools (`agh__tool_list/search/info`), hooks (`agh__hooks_list/info/events/runs/create/update/delete/enable/disable`), extensions (`agh__extensions_search/list/info/install/update/remove/enable/disable`, `agh__extensions_trust_root_set`), bundles (`agh__bundles_list/info/activate/deactivate/status`), resources (`agh__resources_list/info/snapshot`, `agh__resource_list`), MCP (`agh__mcp_status`, `agh__mcp_auth_status/login/logout`) (`internal/tools/builtin_ids.go:9-220`, `internal/tools/builtin/*.go`).
- **Web transport-parity self-warning:** `hooks-extensions.tsx:226-263` renders a banner explaining that hook/policy/extension mutations are UDS/CLI-only when HTTP is bound off-loopback and return 403 — the UI itself documents the known mismatch.

## Transferable Patterns

- {Tri-transport parity table} → applies to the **canonical spreadsheet** because each ET story should carry HTTP + UDS + native-tool entry points as distinct test lanes; a story is not "done" until all exposed transports pass.
- {Status-code + body assertion discipline} → applies to **QA test design** for ET-001…ET-051 because the codebase maps domain errors to precise HTTP codes (400/403/404/409/422/503); status-code-only assertions would miss real regressions (e.g. checksum-mismatch 400 vs unverified 422).
- {Truthful-UI verification guards} → applies to **logistics/UX bug hunting** (operator's phase 3) because the daemon itself re-verifies after mutation (`VerifyInstallVisible`, post-install discoverability). These are the exact spots where "installed but invisible" UX bugs hide.
- {Optimistic-concurrency CRUD} → applies to **resources QA** because `expected_version` conflicts and codec-rejection are first-class failure modes the spreadsheet must cover, not just happy-path writes.
- {Reason-code diagnostics} → applies to **tool/availability QA** because `Availability.ReasonCodes` + `Decision.*Result` give deterministic, assertable explanations for why a tool is hidden/denied — ideal oracle for automated checks.
- {Transport-parity 403 banner} → applies to **off-loopback deployment QA** because it is a documented, reproducible UX divergence the operator should validate end-to-end (web blocked → CLI works).

## Risks / Mismatches

- **Overlap — settings ownership:** `settings/skills` and `settings/hooks-extensions` (and the `mcp-servers`/`hooks` collections) are in this slice's named sources, but a general "settings" slice may also enumerate them. ET-012/013/044/045/046 should be reconciled against any settings-focused slice to avoid duplicate spreadsheet rows; keep the *extensibility-specific* policy fields here and let a settings slice own generic settings plumbing (apply records, restart status).
- **Overlap — bundle-projected resources belong to other slices:** bundle profiles enumerate **agents, jobs, triggers, bridges, and network channels** (`bundles.go:223-301`). Those entities are owned by Runtime/Automation/Network/Bridges slices. ET stories here cover *bundle activation as a unit*; the projected entities' own behaviors (e.g. trigger firing, bridge delivery) are out of scope and must not be duplicated.
- **Overlap — `BundleNetworkSettings` (ET-030)** touches the AGH Network default channel; the Network slice likely owns channel semantics. Captured here only as the bundle-side read; defer channel lifecycle to the Network slice.
- **Overlap — hook events for task/automation/network/coordinator** (`events.go:77-142`) reference subsystems owned by other slices. ET-042 captures the *taxonomy surface* only; the actual firing/dispatch of, e.g., `task.run.post_claim` belongs to the autonomy/task slice.
- **No web UI for several backend-complete surfaces:** bundles (catalog/activate), resources CRUD, MCP servers settings, and MCP OAuth auth appear to have **no dedicated web route** in the named sources — they are API/CLI/agent-backed only. ET-024/025/046/047 are marked accordingly; if a web route exists outside the named sources, the parent should reclassify. This is a *coverage* note, not a defect.
- **Risk — privileged-route HTTP/UDS divergence:** HTTP wraps mutating routes in `privileged`; UDS does not (`routes.go`). A story tested only over UDS will pass where HTTP returns 403/401. The spreadsheet must not mark a mutation "verified" from UDS alone (ET-051 captures the operator-visible symptom).
- **Uncertainty — `agh__mcp_auth_*` and `agh__extensions_trust_root_set` exact backends:** confirmed as registered tool IDs via tests, but the precise dispatch/config target was not read line-by-line (ET-047/050 flagged `Blocked by uncertainty`). The parent or a follow-up read of `internal/tools/builtin/mcp_auth.go` / `internal/cli/mcp_auth.go` / `internal/cli/extension.go` should confirm before QA scripting.
