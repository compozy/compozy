# Initial desktop boot controls — configured webview bridge

- Source: `J-desktop-first-run` / `APP-install-first-run-provision` / `BUG-20260810-boot-controls-unavailable`
- Why automate: Rust webview mocks do not execute the JavaScript loaded by the boot window declared in `tauri.conf.json`, so they cannot prove that the initial configured window receives the minimal command bridge.
- Suggested layer: macOS desktop E2E using the built development app and an isolated stopped runtime.
- Spec sketch: launch the app into `runtime_start_failed`, select `Retry operation` and `Load diagnostics`, assert neither reports `app control unavailable`, independently confirm the retry through `compozy app status`, and confirm `Technical details` renders only the redacted DiagnosticReport. Select `Copy diagnostics` and verify the success announcement. Select `Export diagnostics` and verify that the backend receives explicit consent, creates one local archive, shows no archive path in the UI, and makes no network request. Inspect the archive: it must contain `manifest.json` and may contain only bounded, redacted current-boot `desktop.log` and `desktop-bootstrap.jsonl` tails—never `compozy.log`, raw logs, databases, configuration, credentials, sessions, or transcripts. Repeat after the boot window is closed and recreated; separately prove that retry never terminates an operator-managed runtime.
- Status: proposed
