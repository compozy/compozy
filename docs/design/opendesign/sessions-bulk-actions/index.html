Session bulk actions

sessions-bulk-actions/index.html · 2026-09-11

Pick several sessions, act once. Today every session leaves through its own kebab. This board adds a way to select many rows in the sessions rail — or the dock's Sessions modal, same body — and stop, archive, or delete them together. Nothing changes at rest; the list looks exactly as it does now. Read the contract block, then the four specimens, then the dictionary. Content is illustrative; runtime truth owns values.

What this board is

Bulk actions for the session list. Hover a row and a checkbox appears over its state mark. The first check turns the toolbar into a selection bar: how many, select all, Delete, More (Stop · Archive · Unarchive), Done. Rows stay neutral; a selected row is a plate plus a checked box, never a colour. Delete confirms once for the whole set, shows each session going, and keeps the ones that failed selected so you can try again. With one session selected, everything falls back to today's singular dialogs and menu items — nothing already shipped changes shape.

More actions — the row menu, pluralised and state-gated

DropdownMenu · counts from the selection
Same verbs as one row's kebab, with numbers.

The menu lists what the selection can take: Stop 1 active, Archive 2 stopped, Unarchive 0 archived (disabled), and Delete. Each verb applies to the eligible subset and says so — you never have to deselect the wrong ones first. Stop and Archive act immediately with a toast, exactly as their single-row versions do today. Delete confirms (§04).

In the Archived view the gating flips: Unarchive is live, Archive is not.

04

Delete confirms once for the set, then tells you what happened

SessionDeleteDialog(sessions[]) · confirm → deleting → partial
Today's dialog, plural.

Same frame and copy shape as the single-session dialog: title, one sentence of consequence, ghost Cancel, destructive Delete. New: the list of what you picked, with each session's state word, so a running one can't hide inside a number.

While it runs the dialog can't be dismissed and each row reports back. If some fail, the dialog stays open and says so per row, using the daemon's message; Retry acts on the failed ones only, and closing keeps exactly those selected in the rail.

With one session selected this is the unchanged production dialog.

  • Nothing new at rest. The only permanent change is the hover reveal; the toolbar, the filter, the rows and the kebab are untouched until a box is checked.
  • Neutral selection. Selected = plate + checked box. Accent on the rail while selecting = the checked boxes; the + button leaves with the toolbar.
  • Verbs apply to the eligible subset and say the number. No "deselect the wrong ones first".
  • Selection survives filtering and thread folding; it clears on scope (workspace ↔ all) or Archived toggles, on Esc, and after a batch with no failures.
  • Partial failure keeps the failed ones selected, in the rail and in the dialog. Retry acts on those only.
  • Both hosts. The sidebar and the dock's Sessions modal share SessionList, so the bar, the boxes and the dialog appear in both without a second implementation.
  • Reduced motion: the box appears without a fade, the running dot stops pulsing, the spinner is static. Every state also has its word.
Open questions (runtime truth, decided before the spec)
  • Root with children. Does Manager.Delete cascade to child sessions? If yes, the dialog must list them and the note must say so; if no, selecting the Orchestrator alone is safe as drawn.
  • Fan-out vs bulk route. v1 as drawn: sequential client fan-out over DELETE /sessions/:id (the daemon serialises deletes anyway), which gives per-row results for free. A daemon bulk route is a later optimisation, not a UI change.
  • Running sessions. Delete on a running session is allowed today from the kebab; the note only states the fact. Whether the daemon stops first is its business.
