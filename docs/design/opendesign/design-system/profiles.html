CompozyOS · Chapter 09

Profiles & identity

A profile answers one question: who is working right now. It labels work, it never gates it. That makes identity colour user data — someone picked purple for a client — and data is not allowed to borrow the signal palette. This chapter distils the living boards in ../profiles/ into the reusable grammar: the --id mix formulas, the glyph ladder, owner tags, the switcher, the pickers, enumeration blocks and advisory fills.

01Identity colour is user data, not signal

Identity colour never becomes a token, because it isn't ours — it's a value the user chose and the daemon stored. It flows as a per-element custom property, style="--id:#C26AD6", and every surface derives its fill, ink and ring from that one value with the formulas below. Alongside meter widths, this is the only sanctioned inline style in the system.

Green is not success here. "Personal" is green because someone picked green. That is exactly why identity colour is never allowed to carry state: the moment a green glyph could mean "healthy", the palette stops being readable.

03Owner tags & destination chips

Two chips that look adjacent and mean opposite things, so their shapes are deliberately different. Round means ownership — this thing belongs to that profile. Squarish (radius 6) means a fixed label — a destination, a mode, a constant. Nothing else in the system uses that distinction, which is exactly what makes it readable.

07Advisory blocks

Nothing is wrong — the interface just knows something the user doesn't. Both blocks use an --info-tint fill at radius 10, 12.5/1.5 text and a 14px info glyph. The tone lives in the fill, never in a border. A tinted border on a neutral fill reads as an error frame no matter what the words say.

This session belongs to Client work. You're viewing it from Compozy, so it's read-only here.
This repository declares two profiles. .compozy/profiles.toml names backend and frontend; neither exists on this machine yet.

Two action shapes, one block. A deep-link banner has one obvious answer, so its actions sit at margin-left:auto on the same line. A repo hint may offer several equal-weight actions, so they wrap onto their own line, indented to the text column. Neither ever nags twice — "Ignore for this repo" is a durable answer the daemon stores.

08Rules

P1Identity is not signal. An identity colour never carries state — not running, not failed, not needs-setup. State arrives beside it as a pill, a dot plus a word, or the signal ink from ds-core. Identity hues are user data and may legally collide with green, amber or red.
P2The aggregate is neutral. "All profiles" is deliberately colourless — --badge-fill, a --line-strong ring, --muted ink. An aggregate is not an identity, and giving it one invents a profile nobody created.
P3Quiet until plural. With one profile, the switcher is a plain icon button, aggregate views don't exist, owner tags don't render, and no row mentions profiles at all. The feature appears when a second profile does.
P4Dialogs use the DS dialog frame. Create, rename, archive and delete run on .dialog from chapter 05 — --canvas-soft, --radius-lg, --shadow-overlay carrying the ring. The reference set's bordered .pf-modal is superseded.
P5Settings rows compose .srow. A profile row is a normal settings row with an identity lead in .srow__main — never a bespoke row geometry. Chapter 06 owns the shape; this chapter only supplies the lead.
P6Counts are data, not prose. "18" in 12px --subtle tabular numerals, beside the thing it counts. Never "There are 18 sessions in this profile."

The living boards — switcher, aggregate, picker, lifecycle, settings, extension placements, hints and the palette view — are in ../profiles/ with their contract in DESIGN-NOTES.md. Iterate those boards; never regenerate them.
