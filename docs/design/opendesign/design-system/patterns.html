CompozyOS · Chapter 10

Surface patterns

Chapters 01–09 give you parts. This one gives you whole surfaces: how a listing is arranged, how depth is expressed, what rhythm a detail page keeps, which words and glyphs each status is allowed to use, and which selectors are copied rather than re-drawn. Where a number appears here it was measured from production, not chosen — the detail-page rhythm comes verbatim from the loop-legibility metrics table, and the selectors come from the exported components.

01Listing surfaces

Agents, Skills, Extensions, Sessions, Marketplace, Directories — every inventory in CompozyOS is the same surface with different rows. The strip order is locked, so a user who learns one listing has learned all of them.

L1Strip order is locked: views → search and filters → spacer → display mode. Views lead because they change what the list contains; display mode trails because it only changes how it looks. Never reorder them per surface.
L2Every listing ships Rows and Cards. Rows are the default — denser, scannable, sortable. Cards exist for surfaces people browse rather than operate. Shipping only one is an incomplete listing.
L3No double-encoded facets. A facet is a filter or a column, never both. "provider" as a pill-group view and a column and a filter chip is three controls for one idea.
L4Marketplace cards may lead with icon tiles — the single exception. Third-party extensions have their own marks, and a browsing surface is where a mark earns its space. Every other listing keeps the neutral 34px well.
L5Empty states follow chapter 08. A filtered-empty list keeps its strip live — the way out is the filter you just set, so it must stay on screen.

02Drill-in

Depth grows a breadcrumb in the window head. It never opens a second window and it never spawns a tab — a tab is a peer document you chose to keep, not a place you happen to be standing.

Agents / … / Claude Code / Run 4c19

Level 3 content — the strip survives the descent, so the same views are available at every depth.

Three parents collapse to "…". First and last crumbs stay; the middle becomes a dropdown. The head never wraps and never grows past 44px.

D1Depth is a breadcrumb, not a window. Drilling replaces the head's identity with back button + crumbs. The window count never changes because you clicked a row.
D2Drilling never spawns a tab. Tabs are peers the user deliberately kept open. Descent is navigation, and navigation is reversible with one button.
D3More than two parents collapse to "…". 24px back control, crumbs at 13/510 capped at 150px each, first and last always visible.
D4Every level keeps the strip. Views, search and filters remain available at depth — a child list is still a listing and obeys L1–L5.
D5Documents self-title and never breadcrumb. A live session is a document: its head shows its own name plus a state dot, because it isn't inside anything you navigated.

07Truthful UI & states

A plausible interface is worse than an incomplete one — it costs trust the first time someone acts on it. On any conflict between a nice-looking control and what the daemon can actually do, the daemon wins and the control goes.

U1Every control maps to daemon truth. A control that gates on a payload field cites it in an HTML comment beside the markup, so a reviewer can check the claim without reading the handler. If no field backs it, the control doesn't ship.
U2Every surface designs four states: empty, loading, error, degraded. A surface with only its happy path is half-designed; the other three are where people actually meet it.
U3Liveness degrades honestly. When the stream drops, the reconnecting chip replaces the live badge in place, the last reconciled read stays rendered, and its age is stated in words. Never blank the panel; never keep animating a feed that isn't arriving.
U4Specs gate implementation scope, not preview scope. A board may render a surface the current spec won't build — it renders tagged "proposal" so nobody mistakes it for a commitment.
