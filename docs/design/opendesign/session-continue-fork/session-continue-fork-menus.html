Session continue & fork / menus

Menus and entry points

Two verbs in the two places secondary session verbs already live, and one verb on the message. The row kebab and the window's More-actions menu gain Continue with another agent… and Fork session… right after Rename. A user message gains Fork from here beside Rewind to here. Nothing gets a new icon in the head, nothing lands on the composer, nothing joins the bulk bar. Two existing surfaces change copy: the dead-runtime notice says Restart in a new session, and a turn that failed for quota offers Continue instead of only "wait and retry".

What this board is

The entry points. Where a person starts a continue or a fork: the row kebab in the session list, the overflow menu in the session window head, and the action row under a user message. Both menu items open a dialog (dialogs board); "Fork from here" opens the Fork dialog with that message as the fork point. The two copy-only deltas on the dead-runtime notice and the provider-error marker are drawn here because they are the other two ways into the same dialogs.

The row kebab — two new verbs between Rename and Stop

US-001.AC-1 · US-006.AC-1 · US-001.EC-1 EC-2 · VC-01 VC-02
Same menu, two more lines.

The kebab already carries the verbs that act on one session. Continue and Fork are singular verbs that create one child from this row, so they belong here — after Rename (the only other non-lifecycle verb) and before the lifecycle group. Neither is destructive; neither gets a separator of its own.

Both items are gated by the same rule as Rename: user-controllable rows only. Spawned workers, coordinators and system sessions keep today's menu. An archived row keeps today's menu too — you unarchive first.

Fork from here — beside Rewind, creates instead of removes

US-007.AC-1 AC-2 · US-007.EC-2 EC-5 · VC-04 VC-05
Same row, opposite consequence.

Rewind to here cuts this session. Fork from here starts a second session that ends at this turn and leaves this one alone. They share the row, the size, the gates: durable user messages only, never an optimistic tail, never a read-only thread, never an assistant message.

While the thread runs, a rewind is pending, or a rewind is blocked, both buttons disable together — a moving transcript has no fence to fork from.

Dead runtime — the notice stops saying "fork"

US-012.AC-1 · VC-21 · copy only
One word, so "fork" means one thing.

Today the notice offers Fork into a new session, which creates an empty child and lands it in this window. That is a restart, not a fork — nothing is carried over. With Fork session… now meaning "same agent, same conversation", the notice says Restart in a new session. Behaviour, landing, and the danger banner are untouched; the create request records lineage_kind: "recovery" so the child never shows an origin pill.

A turn failed for quota — Continue is offered, never taken for you

US-004.AC-1 AC-2 · VC-22
The daemon names the next step; the marker shows the door.

When a prompt fails with provider_rate_limited or provider_auth_required on a user session and the daemon's next_action is handoff, the marker's next-step sentence changes and a ghost button opens the Continue dialog with this session as the source. The session stays available, exactly as today. No policy, no timer, no automatic switch — an offer.

Other next actions (login, bind_secret, inspect, retry) render as they do now.

  • Present only when true. The items exist for user-controllable, non-archived rows; the message action exists for durable user messages on a non-read-only thread. Absent, not disabled, when the rule fails (US-001.EC-1, US-007.EC-2).
  • Disabled only while busy. Pending row action, controlsBusy, running thread, pending or blocked rewind — the same gates the neighbouring verbs use.
  • No capability hint here. Native fork versus replay seed is decided by the daemon and shown inside the dialog's context line, never on a menu item.
  • No new head icon, no composer item, no bulk verb. Bulk actions stay delete-class verbs pluralised from the kebab (sessions-bulk-actions board).
  • Landing after success is the dialog's "Open in" choice — New window by default — so this row and this window stay as they were.
