S2

The indicator — one control, one meaning

28px · info ink · no count, no pulse, no menu
A sibling, not a new speciesThe indicator takes the exact geometry of the bell and the settings cog it sits with: a 28px control, rounded-md, a 16px Lucide glyph at the 1.75 stroke. Only the ink differs — --color-info, the section's own "update available" tone — so the bar gains one quiet colour exactly when something is waiting, and none the rest of the time.

Why an arrow and not a dotA 6px dot floating in chrome is easy to miss and says nothing on its own; an upward arrow-in-circle says "there is a newer version" through shape as well as colour, which keeps colour from being the only channel. The glyph is also the only place in the bar where signal ink appears, so it needs to survive a glance without a badge, a count, or a pulse.

VC-12

Hidden — nothing available

the bar almost always looks like this
Absent from the DOMNot display:none, not visibility:hidden, not an empty 28px slot holding space. When the daemon reports no available update on either track, the control is simply not rendered — the cluster closes up and the bar returns to its resting monochrome (US-029.AC-2).

VC-13

Available — one or both tracks

one visual state · detail belongs to S1
Not a summaryRuntime only, app only, or both render the same control: no count, no "2", no dropdown, no hover card. The bar's job is to say that something is waiting; which track, which versions, and what to do about it are the section's job. Activation navigates there.

VC-14

Focus-visible — keyboard

shipped 2px ring · Enter or Space navigates
Reachable, then usefulThe control joins the natural tab order between the ⌘K chip and the settings cog. Focus paints the shipped ring (--shadow-focus-ring: 2px at 50% white, ≥3:1 on the glass) — the ink does not change, so focus and state stay separate signals. Enter or Space lands on Settings → General with the Updates section in view (US-029.AC-4).

VC-15

Suppressed — an update operation is live

applying · staged · failed → the bar says nothing
The offer is overOnce an operation exists the indicator has nothing left to offer, so it disappears the moment apply is accepted and stays gone through applying, staged, and failed (US-029.EC-4). Progress and errors live only in the section — the menubar never grows a progress ring, a percentage, or an error badge. Identical DOM to VC-12: no element at all.

Visibility contract

one predicate, computed from the same payload as S1
Shown only when an offer existsThe predicate is narrow on purpose: an available update on either track, and no live operation. Everything else — including states that clearly need attention, like failed — belongs to the section, because the menubar cannot say what to do about them.

Same in a browserThe SPA has no desktop awareness: the indicator is rendered from the daemon payload, so a plain browser tab pointed at the same daemon shows the same bar with the same control — including on a host with no desktop app, where only the runtime track can ever produce the offer (US-029.AC-3).
One component, one payload, zero user-agent branching — no bridge, no isDesktop, no shell detection.
