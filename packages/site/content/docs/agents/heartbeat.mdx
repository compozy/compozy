description: Optional HEARTBEAT.md authored wake/reentry policy plus runtime session health, advisory wake decisions, and managed authoring surfaces.
---

`HEARTBEAT.md` is an optional authored wake/reentry policy beside an agent's `AGENT.md`. It guides
how an already eligible session should reorient when CompozyOS delivers a synthetic wake. It is not
liveness, not task ownership, not a scheduler, and not a durable work queue.

`HEARTBEAT.md` always coexists with two separate runtime authorities:

- **Session health.** Metadata-only presence, attachability, and wake eligibility maintained by
  the daemon. It never injects prompts or renews task leases.
- **CompozyOS Heartbeat wake service.** Evaluates the latest valid `HEARTBEAT.md` snapshot plus session
  health, applies cooldown and coalescing, and dispatches one synthetic wake prompt. It never
  creates, claims, completes, fails, releases, or renews `task_runs`.

<OperatorNote>
  Four runtime concepts share the word "heartbeat". Keep them separate before writing
  `HEARTBEAT.md`: task-run lease heartbeat (owned by `task_runs` + `ClaimNextRun`), session activity
  heartbeat (owned by `[session.supervision]`), session health (metadata-only daemon state), and
  authored wake policy (`HEARTBEAT.md` + `[agents.heartbeat]`). Authored policy never overrides any
  of the other three.
</OperatorNote>

## Where HEARTBEAT.md lives

```text
~/.compozy/agents/<agent>/AGENT.md
~/.compozy/agents/<agent>/HEARTBEAT.md          # optional
<workspace>/.compozy/agents/<agent>/HEARTBEAT.md
```

`HEARTBEAT.md` follows the same first-wins discovery as `AGENT.md` and `SOUL.md`. A missing file
disables wake policy for that agent without making any session unhealthy.

## File format

`HEARTBEAT.md` is Markdown with optional strict YAML frontmatter and a body that is bounded
guidance only.

```text
---
version: 1
enabled: true
summary: "Reorient, inspect assignments, and claim only through CompozyOS task APIs."
preferences:
  min_interval: "30m"
  active_hours:
    - timezone: "America/Sao_Paulo"
      start: "08:00"
      end: "20:00"
  quiet_windows:
    - timezone: "America/Sao_Paulo"
      start: "22:00"
      end: "08:00"
context:
  include:
    - self
    - session_health
    - task
    - inbox_summary
---

When CompozyOS wakes you, inspect `/agent/context` and your inbox before acting.
Use `compozy task next` to obtain claim authority; do not assume work is owned.
If nothing is claimable, return a concise no-op summary.
```

| Field                       | Type         | Authored | Notes                                                                                    |
| --------------------------- | ------------ | -------- | ---------------------------------------------------------------------------------------- |
| `version`                   | integer      | optional | Snapshot schema version.                                                                 |
| `enabled`                   | boolean      | optional | Local toggle; the runtime still consults `[agents.heartbeat].enabled` and config bounds. |
| `summary`                   | string       | optional | Short reentry hint surfaced in status responses.                                         |
| `preferences.min_interval`  | duration     | optional | Authored minimum interval; clamped to `[agents.heartbeat].min_interval`.                 |
| `preferences.active_hours`  | array        | optional | IANA timezone allow windows. Multi-window union, midnight crossing supported.            |
| `preferences.quiet_windows` | array        | optional | IANA timezone deny windows; subtracted from `active_hours`.                              |
| `context.include`           | string array | optional | Hints about what context the agent should re-read on wake.                               |
| Body                        | Markdown     | optional | Bounded reentry prose. Truncated at `[agents.heartbeat].max_body_bytes`.                 |

Omitting `context` enables the configurable proactive collectors. An explicit
`context: {include: []}` disables those collectors and survives save, reload and rollback.
Pending `automation_events` are always collected for an always-on instance, independently of that
selection. See [event targets](/docs/automation/events#send-an-event-to-an-always-on-check).

The `work_log` collector reads the workspace's `.compozy/work-log.md` and reports `[ ]` entries older
than 30 minutes, oldest first: up to 9 items, then `work:more` if there are others, and
`work:log-truncated` when the file is larger than 64 KiB. A missing file reports nothing. User and
global instances have no work log. See
[Deliver small work](/docs/examples/deliver-small-work).

The parser is strict. Forbidden operational fields are explicit. Time-window predicates use IANA
timezone names; fixed offsets fail validation with `heartbeat_invalid_timezone`. If file
preferences exceed config bounds, the resolver clamps to config and emits a
`heartbeat_preference_clamped` diagnostic instead of silently dropping the value.

### Forbidden fields

`HEARTBEAT.md` cannot define liveness, claim authority, scheduler intervals,
provider configuration, capabilities, lease duration, raw claim tokens, recurring model loops, or
queue ownership. Use the linked surface instead:

| Forbidden in `HEARTBEAT.md`                            | Belongs in                                |
| ------------------------------------------------------ | ----------------------------------------- |
| Raw claim tokens, lease duration overrides             | `task_runs` + `ClaimNextRun` runtime APIs |
| Task status transitions, queue ownership               | `task_runs` + task CLI/API                |
| Scheduler sweep cadence, claim cadence                 | Scheduler config                          |
| Provider config, model selection, tool grants          | `AGENT.md` and `[providers]`              |
| Capabilities, hooks, MCP servers, permissions          | `AGENT.md` and `config.toml`              |
| Recurring model pings or persistent heartbeat sessions | Not supported in MVP                      |

## Snapshot digest and resolution

`HEARTBEAT.md` digest covers `schema_version`, normalized body, canonical frontmatter JSON, and a
canonical digest of the resolved `[agents.heartbeat]` config subset. Direct file edits resolve at
daemon load and at wake-decision time when the source digest or config digest has changed; the
resolver is metadata-only and never calls the model.

Validation outcomes:

- **Missing file:** `present=false`, no diagnostics, sessions remain healthy and wakeable.
- **Valid file:** snapshot stored in `agent_heartbeat_snapshots`, latest valid snapshot drives
  wake decisions.
- **Invalid file:** wake policy is disabled for that agent; status returns `heartbeat_invalid`
  with diagnostics. Normal sessions and task APIs still work.

## Session health

Session health is a metadata-only runtime primitive. It exists whether or not `HEARTBEAT.md` is
authored and is the only authority for whether an idle session is wake-eligible.

| Field                  | Meaning                                                      |
| ---------------------- | ------------------------------------------------------------ |
| `state`                | `idle`, `prompting`, `stopped`, `detached`.                  |
| `health`               | `healthy`, `degraded`, `stale`, `dead`, `unknown`.           |
| `active_prompt`        | An ACP/user prompt is currently in flight.                   |
| `attachable`           | The runtime can deliver a prompt to this session.            |
| `eligible_for_wake`    | Wake decisions may target this session.                      |
| `ineligibility_reason` | Closed enum from the wake-state reason set, never free text. |
| `last_activity_at`     | Last real activity update from active prompts.               |
| `last_presence_at`     | Last metadata-only presence touch.                           |
| `updated_at`           | Last health write.                                           |

Health updates never inject prompts, never renew task leases, and never call the model. On daemon
restart, CompozyOS recomputes health from runtime/session state before any wake consumer runs; stale
rows alone cannot make a session wake-eligible.

`compozy session health`, `compozy session status`, and `compozy session inspect` expose this state with
`-o json` for agent and operator consumption. There is intentionally **no** `compozy session
heartbeat` command — that name conflates liveness with authored wake policy.

## Wake decision flow

```text
AGENT.md + capabilities + config
        │
        ▼
HEARTBEAT.md ── resolve ──► snapshot
                                 │
session.health ──────────────────┤
                                 ▼
scheduler/manual/harness ──► HeartbeatWakeService
                                 │
                                 ▼
        ┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────────┐  ┌────────┐
        │  sent   │  │ skipped │  │ coalesced│  │ rate_limited│  │ failed │
        └─────────┘  └─────────┘  └─────────┘  └─────────────┘  └────────┘
                                 │
                            synthetic wake prompt
```

Wake guarantees:

1. Manual wake resolves the current `HEARTBEAT.md` through the same policy loader as status,
   including repository edits without an authoring revision. A real wake persists its snapshot; a
   dry run evaluates without writing one. Scheduler and harness wakes use persisted snapshots.
2. Wake never calls `ClaimNextRun`, never creates `task_runs`, never renews leases, and never
   issues raw claim tokens.
3. Wake serializes with the session prompt gate. If a user/model prompt starts concurrently, wake
   records `session_prompt_active_race` and skips delivery.
4. The synthetic prompt names the wake reason and policy snapshot id, instructs the agent to
   inspect `/agent/context`, session state, inbox, and task APIs before acting, and never implies
   claimable work exists.

Manual operator/agent wake:

```bash
compozy agent heartbeat wake reviewer --session sess_123 --json
```

`result` is one of `sent`, `skipped`, `coalesced`, `rate_limited`, or `failed`, and `reason` is a
deterministic enum value: `wake_sent`, `heartbeat_disabled`, `heartbeat_invalid`,
`heartbeat_no_policy`, `heartbeat_rate_limited`, `cooldown_active`, `quiet_window`,
`session_not_found`, `session_unhealthy`, `session_not_attachable`, `session_prompt_active`,
`session_prompt_active_race`, `synthetic_prompt_failed`, or `wake_coalesced`.

## Managed authoring

Mutating `HEARTBEAT.md` always goes through the managed authoring service. CLI, HTTP, UDS, and
Host API share the same DTOs, validation, CAS, and revision audit. Direct file writes from hooks,
extensions, tools, MCP sidecars, or web code are forbidden.

| Action   | CLI                                | HTTP                                         | UDS                        | Host API                    |
| -------- | ---------------------------------- | -------------------------------------------- | -------------------------- | --------------------------- |
| Inspect  | `compozy agent heartbeat inspect`  | `GET /api/agents/{name}/heartbeat`           | `agent.heartbeat.inspect`  | `agents/heartbeat/get`      |
| Validate | `compozy agent heartbeat validate` | `POST /api/agents/{name}/heartbeat/validate` | `agent.heartbeat.validate` | `agents/heartbeat/validate` |
| Write    | `compozy agent heartbeat write`    | `PUT /api/agents/{name}/heartbeat`           | `agent.heartbeat.put`      | `agents/heartbeat/put`      |
| Delete   | `compozy agent heartbeat delete`   | `DELETE /api/agents/{name}/heartbeat`        | `agent.heartbeat.delete`   | `agents/heartbeat/delete`   |
| History  | `compozy agent heartbeat history`  | `GET /api/agents/{name}/heartbeat/history`   | `agent.heartbeat.history`  | `agents/heartbeat/history`  |
| Rollback | `compozy agent heartbeat rollback` | `POST /api/agents/{name}/heartbeat/rollback` | `agent.heartbeat.rollback` | `agents/heartbeat/rollback` |
| Status   | `compozy agent heartbeat status`   | `GET /api/agents/{name}/heartbeat/status`    | `agent.heartbeat.status`   | `agents/heartbeat/status`   |
| Wake     | `compozy agent heartbeat wake`     | `POST /api/agents/{name}/heartbeat/wake`     | `agent.heartbeat.wake`     | `agents/heartbeat/wake`     |

CAS contract: every mutating transport carries `expected_digest` in the request body. HTTP
`If-Match` headers are explicitly rejected with `heartbeat_if_match_header_unsupported` so CLI,
HTTP, UDS, Host API, and SDKs share one CAS shape. The CLI alias `--if-match` maps to
`expected_digest`.

```bash
compozy agent heartbeat validate reviewer --file HEARTBEAT.md --json
compozy agent heartbeat write reviewer --file HEARTBEAT.md --if-match sha256:1234... --json
compozy agent heartbeat status reviewer --json
```

There is no `compozy agent heartbeat refresh` command in MVP. Managed writes create new snapshots,
and manual wake resolves the current file even when no managed write has created a snapshot.

Recent wake events include proactive checks: `timer` identifies scheduled checks and
`instance_check` identifies manual instance checks. These retain their check outcomes
(`quiet`, `reported`, `cancelled`, `skipped`, or `failed`) alongside legacy heartbeat wakes
(`scheduler`, `manual`, and `harness_reentry`). Existing audit rows remain readable after upgrade.

## Diagnostics

Validation and wake responses use one diagnostic shape across CLI, HTTP, UDS, and Host API.
Common deterministic codes:

| Code                                                   | Meaning                                                                   |
| ------------------------------------------------------ | ------------------------------------------------------------------------- |
| `heartbeat_disabled`                                   | `[agents.heartbeat].enabled=false` or the file disables policy locally.   |
| `heartbeat_invalid`                                    | Parser/validation rejected the body or frontmatter.                       |
| `heartbeat_conflict`                                   | `expected_digest` did not match.                                          |
| `heartbeat_if_match_header_unsupported`                | HTTP `If-Match` header was sent; use `expected_digest` instead.           |
| `heartbeat_rate_limited`                               | The agent exceeded `max_wakes_per_cycle` for the current scheduler cycle. |
| `heartbeat_no_policy`                                  | No current manual policy or stored scheduler/harness snapshot exists.     |
| `cooldown_active`                                      | The session is inside `wake_cooldown` from a prior wake.                  |
| `quiet_window`                                         | Wake fell inside an authored quiet window.                                |
| `session_not_found`                                    | The target session id was not resolved.                                   |
| `session_unhealthy` / `session_not_attachable`         | Session health blocks delivery.                                           |
| `session_prompt_active` / `session_prompt_active_race` | An active prompt is in flight or started during the wake gate.            |
| `synthetic_prompt_failed`                              | Synthetic prompt enqueue failed.                                          |
| `heartbeat_preference_clamped`                         | An authored preference was clamped to a config bound.                     |
| `heartbeat_invalid_timezone`                           | A time-window timezone was missing or not an IANA name.                   |

Logs and audit rows redact actor identities, never include raw claim tokens or full prompt
transcripts, and use workspace-relative paths.

## Boundaries with other authorities

- `HEARTBEAT.md` is **not** task-run lease heartbeat. `task_runs` + `ClaimNextRun` +
  `HeartbeatRunLease` remain the only ownership authority and never read `HEARTBEAT.md`.
- `HEARTBEAT.md` is **not** session activity supervision. `[session.supervision]` continues to own
  active prompt activity timers, runtime progress, the in-flight turn warning and inactivity stop,
  and idle runtime release. See
  [Session Lifecycle → Runtime activity supervision](/docs/sessions/lifecycle).
- `HEARTBEAT.md` is **not** session health. Health is metadata-only and lives in
  `session_health`. `HEARTBEAT.md` consumes health; it never implements it.
- `HEARTBEAT.md` is **not** a scheduler. Scheduler eligibility runs first; the wake service is
  consulted afterward and never claims work.
- `HEARTBEAT.md` does **not** create work. Wake state and wake events are audit and coalescing
  records; no row in `agent_heartbeat_wake_*` is a claimable queue entry.

## Common errors

| Error                          | Cause                                                                         | Fix                                                                  |
| ------------------------------ | ----------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| `heartbeat_invalid_timezone`   | A time window used a fixed offset or unknown zone.                            | Use IANA names such as `America/Sao_Paulo` or `UTC`.                 |
| `heartbeat_preference_clamped` | File `min_interval` was below `[agents.heartbeat].min_interval`.              | Either align the file or raise the config bound.                     |
| `heartbeat_conflict`           | `expected_digest` did not match the current file digest.                      | Re-read the digest with `compozy agent heartbeat inspect` and retry. |
| `heartbeat_rate_limited`       | Wake attempts exceeded `max_wakes_per_cycle` for the current scheduler cycle. | Wait for the next cycle or relax the cap.                            |
| `quiet_window`                 | The current instant fell inside an authored quiet window.                     | Wait for the active window or adjust the policy.                     |

The `monitors_fired` collector retains its configuration name, but includes only
undelivered or interrupted monitor wakes. Successfully admitted wakes do not
change the check digest when retained or removed from monitor history.

Instance reads expose optional `next_wake` with `kind`, `description`, and an
optional `at` timestamp. The earliest known timer or enabled check wins; when
none has a time, an active monitor can still supply its description without
an invented timestamp. `next_wake_at` remains the check schedule. The `now`
field is empty unless the main session is working.

Always-on mains and their descendants receive daemon-composed doctrine about
authorization, bounded follow-ups, daemon monitors, refusal handling, delegation,
and durable context. Session identity and ancestry select it, not the agent name
or Orchestrator role. Only the main receives the direction to start Goals in
another session. This guidance does not itself enforce Goal refusal.

The first prompt after a completed provider compaction includes a short notice
and full situation sections. Subsequent prompts reuse unchanged sections again.
This applies to all sessions and does not request compaction or replay input.

When known context usage reaches `agents.always_on.rotation_threshold`, the
current always-on main receives one reminder on its next prompt to preserve
durable facts and its next step. A usage drop re-arms the reminder and restores
full situation sections. Unknown usage sends no reminder, and this mechanism
starts no turn.

Goal `set` and `replace` on the current always-on main return
`goal_on_instance_main`; start the Goal in another session. Existing Goals keep
their status and lifecycle controls. An active Goal also blocks main-session
rotation until it settles.

Instance mains rotate for context only after a real provider context-exhaustion
refusal. Usage percentage alone sends a reminder. Exhaustion persists the main
session ID until successful rotation. Rotation retains the existing brief and
dependency gate; a deferred report lists blocking dependencies, and reconciliation
retries on later ticks. Active monitors, queued input, and active Goals can keep
an exhausted main blocked until the operator resolves them.

## Pause autonomous work

Pausing an always-on instance holds autonomous input for its main session and descendants.
A running work turn finishes. A running check-in is cancelled without increasing
fatigue. Human prompts still run, including a child started from a human turn, and do
not resume the instance. Pending proposals and their approval deadlines remain in place.

By default, 300 unattended turns pause an instance with reason `unattended`, one report
and one notification. Set `[agents.always_on].unattended_turn_limit = 0` to disable this
brake. A batch counts once; quiet checks and managed Goal/Loop turns do not count.
Human prompts, marking reports seen, operator approvals or clarification answers, and
resume reset the counter. Keeping a window open does not reset it.

```sh
compozy agent instance show triage --workspace my-project -o json
compozy agent instance resume triage --workspace my-project
```

Instance reads include `unattended_turns`, `unattended_turn_limit` and `held_wakes`.
Only the operator can resume a manual, fatigue or unattended pause. Resume releases
held input and restores only Goals and Loops paused by the instance; an independently
paused run stays paused. Directly resuming a run while its instance is paused returns
`agent_instance_paused`. Held input and counters survive daemon restart. A stopped
main restarts for delivery; stopped descendants retain their queues. Archiving the
instance cancels its held rows.

In the app, a brake pause appears in the agent's main session as "Paused until you're
back", with the number of steps, how many things are waiting, and **Resume**. If you
were away, the While you were away card says when it paused and offers **Resume** in
place. When two or more agents in a project paused this way, the `+N` crew panel offers
**Resume all**. An agent's hover card shows what wakes it up next.

Manual, fatigue, unattended and unknown pauses hold monitor wakes throughout the
instance's lineage. Definition pauses (`definition_missing` or
`definition_not_always_on`) hold only its main sessions, including old mains after
rotation. Dispatched children continue their monitor wakes and agent messages, and
their turns still count toward the unattended limit. Reaching that limit replaces
the definition pause with `unattended` and holds the whole lineage. A prepared Goal's
ordering boundary does not hold normal child continuations during a definition
pause; the Goal itself retains its explicit pause guard. Manually pausing an instance
that has a definition pause replaces it with the full lineage brake; other existing
safety pauses remain unchanged. If an idle-released child also used the removed
definition, its queued work can reload the same runtime from its accepted definition;
new sessions and runtime switches still require an available definition.

Held prompt results and queued inputs include `held_reason` and `held_instance_id`.
A session with held input shows Needs attention; its status includes a `held_input`
work signal with the reason and instance. Holds belonging to an archived instance
report `instance_archived`, since that instance cannot be resumed. Archiving a
paused instance holds its descendants even when the pause was caused by a missing
definition; human input remains available. Restoring or adopting an agent does not
transfer children from a different instance. Quiet windows do not hold monitor wakes. Lost main-session
wakes produce one interrupted report per wake, except shutdown cancellations. A
delivered wake does not trigger another check.

## Check-in sources

Declare external facts under `context.sources`. Each entry has a unique local `id`, exactly one of `script` or `kind`, and optional `with` data (up to 4 KiB). Scripts live in the agent definition's `sources/` folder. Kind names use `<extension>/<kind>`; kinds unavailable in the current workspace remain visible as unavailable.

```yaml
context:
  include: []
  sources:
    - id: deploys
      script: failed-deploys
      with:
        environment: production
```

Run `compozy agent heartbeat sources <agent>` to inspect scripts and effective limits. Review the script, then approve its exact hash with `compozy agent heartbeat sources approve <agent> <script>`. In the app, the Heartbeat page shows a notice above Sources for every declared script that waits, before the first check and while the agent is paused, and the menubar bell lists them under Scripts to approve. Both approve the same exact hash. Use `--sha256` and `--yes` for a noninteractive approval. Only the operator may approve or revoke; agent credentials are rejected. Editing the script requires a new approval. Approve self-contained scripts: commands and files they load remain trusted operator input outside the approved hash. Extension-owned scripts never execute.

A script receives version 1 JSON on stdin with `source_id`, `params`, committed `state`, `limits`, `workspace`, `now`, and `dry_run`. Return one JSON object with `items` (unique `key`, `title`, optional `summary`, `url`, `attributes`), optional next `state`, and `more`. Page within `limits.max_items`; never advance state past returned items. Exit zero with `{"items":[]}` when nothing changed. Omitting `state` preserves the previous cursor.

Each item requires a unique stable `key` matching `[A-Za-z0-9][A-Za-z0-9._:/#@+-]{0,199}` (ASCII, at most 200 bytes) and a nonempty `title` of at most 200 Unicode characters. `summary` is at most 1 KiB; the daemon shortens longer summaries at a UTF-8 boundary. `attributes` JSON is at most 2 KiB, and `url` is at most 2 KiB of UTF-8. Invalid keys, titles, attributes or URLs fail the poll with `source_output_invalid`. `[agents.heartbeat.sources].max_output_bytes` caps script stdout and the encoded extension result before summary shortening (`source_output_too_large`); `max_state_bytes` bounds opaque state. Item text is redacted and fenced as untrusted input before triage.

Polls run before model work. Empty or unchanged source digests skip the model even when standing guidance is present, and source-backed checks keep their configured cadence. Item text is untrusted data. State commits only after a successful check, or on an empty skipped batch; failures retry from the previous state. `compozy agent instance check <agent> --dry-run` polls without changing state or status, including on a paused instance.

Scripts run a private copy of approved bytes with the workspace as cwd. They receive `PATH`, `HOME`, `LANG`, `TMPDIR`, `USER`, `COMPOZY_SOURCE_ID`, `COMPOZY_AGENT`, and explicitly allowed daemon environment variables; they never receive `session_env`. Stdout, state, runtime and stderr are bounded. Upgrade every daemon reading a file before adding `context.sources`; older daemons reject the new key on downgrade.

Healthy, unapproved and disabled sources are eligible on every check that passes the collection gates, including manual and event-pulled checks. `next_poll_at` is only a failing source’s retry backoff. A batch with `more: true` schedules the next timer check at `agents.heartbeat.min_interval` plus jitter, including when triage skips an unchanged digest. Other source-backed checks use the resolved agent cadence without quiet backoff. Reserved `COMPOZY_*` names are rejected in `env_allow`.

## Check-in tools and authority

A check-in's final assistant message must contain only `NOTHING_TO_REPORT` or one JSON
object with `proposals`. A single Markdown fence and plain commentary around a proposal
object are tolerated. Multiple objects or fences, braces or array brackets in surrounding
commentary, and a sentinel mixed with proposals are rejected as ambiguous. The envelope
and proposal fields remain strictly validated; earlier assistant messages and tool output
are not parsed as proposals. Invalid replies keep the `triage_output_invalid` reason and
include a static validation category in the redacted report detail: `framing`,
`ambiguous_reply`, or `schema`.

A check-in that reaches the model can use native and MCP read tools through the
hosted gateway. Provider built-in tools remain in their confirmed read-only mode.
The instance's current main-session permissions and tool grants remain the ceiling.
An empty or unchanged digest still starts no model turn.

```yaml
check_ins:
  allow_writes: [compozy__notify]
  max_tool_calls: 10
  max_write_calls: 1
```

Reads need no write opt-in. Writes require a matching selector, approval of the
exact authority digest, and a main session that could run the call without asking.
The native writable set is `compozy__notify`. Other native mutations must be proposed
for the main session. MCP selectors accept an exact canonical ID or `mcp__<server>__*`.

Claude check-ins run in Claude's `plan` mode, and Claude currently declines approved
write tools while in that mode. Reads and actions work on Claude; for approved check-in
writes, run the agent on Codex, or declare an action so the main session performs the
change.

A check-in never asks anyone anything. A write the main session would need approval
for is denied `check_in_write_needs_approval`, and no approval request is created.
`compozy__clarify` and every other tool that opens an operator interaction are always
denied (`check_in_tool_not_writable`), even when classified as reads. When the
instance has no main session, every call, read or write, is denied
`check_in_no_main_session`.

The authority block is `allow_writes`, both caps, every action (`id`, `title`,
`instructions`, `auto_accept`), and the `read_only_tools` overrides in the agent's
MCP declarations. Changing any of them changes the digest. Review and approve the
block with `compozy agent heartbeat authority show <agent>` and
`compozy agent heartbeat authority approve <agent>`. For scripts, approve with
`--sha256 <digest> --yes`. Revoke with `heartbeat authority revoke <agent>`.
`heartbeat write` displays the block before asking for approval; noninteractive
writes can use `--approve-authority --yes`. A save never approves implicitly.
Agent credentials cannot approve authority.

Until the operator approves a non-empty block, the whole block is ignored:
check-ins get reads only with the daemon's default caps, actions are not offered
to the check-in, `read_only_tools` overrides are not applied (those tools stay
writes in check-ins and in the main session), and every proposal waits for a pick.
The instance shows "Check-in changes need your approval" and one notification fires
per digest.

If HEARTBEAT.md cannot be read or validated, including caps above the daemon limits,
its authority is treated as unapproved. Main-session tools remain available with
MCP overrides withheld. Tool descriptors expose `check_in_writable` alongside
`access`; the editor uses this value for its write-tool choices.

Each tool attempt is audited with its access class, outcome and redacted arguments;
results are not retained. `instance check-ins <agent> --occurrence <id> -o json`
lists calls. Without JSON output, `instance check-ins` includes WHEN, OUTCOME,
TOOLS and PROPOSALS columns; the proposal summary reads, for example,
`1 auto-accepted, 1 waiting`. `instance reports` text includes each proposal's pick
state and `auto_accept_status`, plus total tools, completed/uncertain writes and
denials. An otherwise quiet check-in that wrote
publishes an activity report, including calls that may have changed something.
Cancellation still discards pending source state.

Operator-authored MCP declarations may set `read_only_tools: [raw_tool_name]` for
unannotated read tools. Extension and marketplace declarations cannot set this
classification. `destructiveHint: true` always makes a tool a write, including in
main sessions. Existing files gain reads only. Upgrade every daemon reading a file
before adding the new keys; older daemons reject unknown frontmatter.

Set `[agents.always_on].check_in_tools = "disabled"` to disable hosted tools in check-ins.
Check-ins then launch with no MCP servers and no tools, and
check-in records show `tools_status: disabled`. Each record shows `unavailable` when
the provider's read-only mode refused hosted tools.

### Let a check-in search Linear

Give the agent the Linear MCP server in `AGENT.md`, as for any session:

```yaml
mcp_servers:
  - name: linear
    transport: http
    url: https://mcp.linear.app/mcp
```

Then tell its check-ins what to look for in `HEARTBEAT.md`, and keep writes off:

```markdown
---
version: 1
check_ins:
  allow_writes: []
---

Look for new Linear issues assigned to me that have no comment from me yet.
Propose one item per issue that needs me.
```

When a check-in reaches the model, it calls `mcp__linear__search_issues` (a read)
with the agent's own Linear credentials and proposes what it finds. The report
shows "Check-in used N tools", and
`compozy agent instance check-ins <agent> --occurrence <id> -o json` lists each call.
If a Linear read tool has no `readOnlyHint`, it is a write and denied
`check_in_write_not_allowed`; list its raw name under `read_only_tools` in the
operator-authored declaration and approve the changed authority.

## Actions and proposal picks

Declare up to eight actions in `HEARTBEAT.md`. Each action has a unique lowercase
hyphenated `id` (up to 40 characters), a `title` (up to 120 characters),
`instructions` (up to 1,000 characters), and optional `auto_accept` (default false).

```yaml
actions:
  - id: write-report
    title: Write a report
    instructions: Investigate the evidence and write a report. Preserve untrusted fences when relaying evidence.
    auto_accept: true
```

A proposal may name an action. Picking it queues the action instructions followed
by the proposal inside an untrusted fence in the instance's main session. A
proposal without an action queues its title. While the authority is unapproved,
actions are not offered to the check-in and a pick queues the title only. The main
session keeps its own tool permissions; picking grants no additional access.

Auto-accept requires approval of the exact authority digest. Editing any action
(including its title or `auto_accept`) invalidates that approval. Only completed
check-ins on active instances with a main session can auto-pick, after
deduplication and unattended/fatigue checks. The rolling 24-hour limit is
`[agents.always_on].auto_accept_per_day` (default 20, range 0–200). A full queue
leaves the proposal waiting. Auto picks count toward the unattended turn limit.
Pausing or archiving cancels queued auto picks.

Each proposal with an auto-accept action reports `auto_accept_status`: `picked`
when the daemon picked it, otherwise the reason it waited, recorded when the report
was published and never recomputed: `limit` (daily limit reached), `queue_full`,
`unapproved` (authority not approved), `no_main` (no main session), or
`inactive` (the instance was paused, archived, or inactive). Proposals
without an auto-accept action report `none`. An operator pick never shows as
`picked`; its pick record has actor `operator`.

Operators can pick from the CLI with a 1-based proposal number:

```bash
compozy agent instance pick log-triage <report-id> 1 -o json
```

HTTP and UDS use `POST /api/agent-instances/{id}/reports/{report_id}/pick` with
`{"proposal":0}` (0-based). Agent credentials cannot pick. Repeating a pick fails
with `proposal_already_picked`. Report reads expose recorded picks and their queue
state (`queued`, `delivered`, `cancelled`, or `failed`).

## Acknowledge attention

Choose **Mark as seen** in an always-on avatar's hover card to acknowledge old failure attention.
The avatar updates immediately after the server refreshes its state. Pending requests in live
sessions keep the indicator until answered; pending or orphaned requests in stopped sessions
are canceled. A new failure raises attention again.

The local operator can use `compozy agent instance mark-seen <id>` or
`POST /api/agent-instances/{id}/away` for the same acknowledgement. Reports remain in history
and keep their provider delivery state: reading them does not send them to the agent.

### Recovering rejected check-in configuration

A check-in rejected with `triage_config_unavailable` waits up to
`agents.heartbeat.max_interval` before retrying. Applying heartbeat or provider runtime
configuration reschedules affected active instances within their normal resolved cadence
and clears the quiet and failure backoff. A fresh live provider model catalog confirming
the configured triage model also schedules recovery in that profile and workspace.
Paused, archived, disabled, and in-flight instances are left alone. Pending automation
events and unattended-turn counts are preserved.

Instance status and list responses explain the last runtime rejection in the next check's
description. Use `agent_instance_check` to retry manually after correcting configuration.

Manual wake `source` accepts `timer`, `instance_check`, `scheduler`, `manual`, or `harness_reentry`
(default: `manual`). Unknown values return a validation error listing these values.
