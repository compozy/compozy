CompozyOS stores one authoritative window topology per workspace. Each persistent virtual desktop has
one tab bar; a tab holds one window or several windows split side by side. Clients project that same
topology into their own viewport. The daemon, not the browser, validates tabs, split trees, weights,
history, and revisions.

<OperatorNote>
  Window management is workspace state. Deleting a workspace removes its topology. A browser stores
  only its stable client identifier locally.
</OperatorNote>

## Topology and presentation

Every window belongs to exactly one tab, and every tab to exactly one desktop. A tab's content is a
single window or a tree of horizontal and vertical splits whose leaves are windows; split shares are
weights, not pixels, so two browsers with different viewport sizes render one shared arrangement. A
window only opens or closes: it has no position, size, minimized, or zoomed state, and it is always
visible while its tab is active.

Active desktop, active tab, and focused window are client-local. Two browsers on one workspace each
keep their own active tab. Commands that change presentation — desktop switch and window focus —
require an explicit connected `client_id`, so one operator cannot silently redirect another
operator's screen. Each client view has an independent, monotonic presentation revision: these
commands do not advance topology revision, change layout history, or emit extension hooks.

## Revision-safe operations

Read the current topology before changing it:

```bash
compozy layout get --workspace <workspace-id> -o json
```

Every durable CLI mutation requires `--revision`. A successful command advances the workspace
revision once and atomically records the normalized snapshot and event. Layout/topology commands add
one history entry; route navigation and tab activation do not enter or clear layout history.
Preview, validation, rejection, and no-op paths write nothing.

```bash
compozy desktop create --workspace <workspace-id> --revision <revision> --name Build
compozy window open --workspace <workspace-id> --revision <revision> --app tasks \
  --pathname /tasks --search-json '{}'
compozy window navigate --workspace <workspace-id> --revision <revision> --id <window-id> \
  --pathname /tasks/<task-id> --search-json '{"tab":"runs"}'
```

The app ids `jobs` and `triggers` are deprecated: one `automations` app replaced them in v0.4.0
(`--app automations --pathname /automations/jobs/<job-id>`). `--app jobs|triggers`, window
commands, and `window_layout` resources that name them still open Automations on the matching path
and warn. Any other app id that is not registered is refused with `window_manager_invalid_command`
(HTTP 422, "unregistered window app") on HTTP, UDS, the CLI, and native tools, before anything
changes. Saved layouts that named `jobs` or `triggers` migrate permanently. See [Upgrading from v0.3](/docs/automation#upgrading-from-v03).

On `window_manager_revision_conflict`, read the topology again and recompute the semantic action.
Do not replay stale node IDs or weights blindly.

A window's durable `route` contains an internal absolute pathname and canonical JSON-object search
state, so detail/filter state resumes after reload or daemon restart and converges in peer clients.
Add `--client` to `compozy window navigate` only when the same operation should also activate and
focus that explicit client.

## Tabs

New windows open as a new tab right after the active tab (`new_window_policy = "tab"`). Set
`new_window_policy = "beside_focus"` to open them split to the right of the focused window instead.
An explicit placement wins over the policy: `--stack-target <window-id>` opens a tab right after that
window's tab, and `--tiled` splits beside the client's focus.

In the app, the tab bar at the top of the work area lists every tab of the active desktop. A tab
shows the icon and title of its lead window (the one you focused last); a split tab shows up to three
icons and a member count. Tabs shrink to fit, down to icon-only, and then the bar scrolls and offers a
list of the tabs that do not fit. Pinned tabs sit at the left, icon-only. The bar is one tab stop:
Left and Right move between tabs and Home and End jump to the first and last. Middle-click closes
a tab.

Drag a tab along the bar to reorder it. Right-click a tab, or focus it and press Shift+F10, for the
items below; an item that cannot apply is absent rather than disabled (no **Reopen closed tab** when
nothing was closed, no **Close tabs to the right** on the last tab):

| Item                                                                                              | Does                                                                         |
| ------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| **Pin tab** / **Unpin tab**                                                                       | Pins the whole tab to the left of the bar                                    |
| **Move left**, **Move right**                                                                     | Moves the tab one place within its pinned or unpinned range                  |
| **Split with ▸**                                                                                  | Puts another tab's windows beside this tab's                                 |
| **Arrange ▸**                                                                                     | **Main and stack**, **Columns**, **Grid**, and **Balance sizes** for a split |
| **Move to desktop ▸**                                                                             | Moves the whole tab, splits included, to another desktop; you stay here      |
| **Close tab**                                                                                     | Closes the tab (absent on a pinned single-window tab: unpin it first)        |
| **Close other tabs**, **Close tabs to the right**, **Close tabs to the left**, **Close all tabs** | Close unpinned tabs only                                                     |
| **Reopen closed tab**                                                                             | Brings back the most recently closed tab or window where it was              |

From the command line:

```bash
compozy window activate <window-id> --workspace <workspace-id> --revision <revision> --client <client-id>
compozy window reorder <window-id> --workspace <workspace-id> --revision <revision> --index 0
compozy window pin <window-id> --workspace <workspace-id> --revision <revision>
compozy window close --workspace <workspace-id> --revision <revision> --id <window-id> --scope right
compozy window reopen --workspace <workspace-id> --revision <revision>
```

`window close --scope` accepts `tab` (default: one window), `group` (every window of the tab, pinned
or not), `others`, `right`, `left`, and `all` (unpinned tabs only). Closing the last window of a
pinned tab is refused until you unpin it. Closing the last tab of a desktop leaves a New Tab window.

## Splits

Drag a tab down out of the bar into the content area: the half of the window under the pointer that
is nearest to it highlights, and dropping puts the tab's windows there. Near the outer edge of the
content area the highlight covers the whole edge of the tab instead, for a full-height or full-width
window. Drag a window by its header onto another window of the same tab to move it to that side;
hold Shift (`swap_modifier`) while dropping to swap the two windows instead. Escape cancels a drag
and restores the bar as it was.

The line between two split windows is a seam. Drag it, or focus it and use the arrow keys (2% per
press, 10% with Shift), to resize the windows on either side; double-click it to give both sides the
same size. Each app keeps its own minimum size: a seam stops, and a drop target is not offered, where
a window would get smaller than that. When a split does not fit, the app shows one of its windows at
a time with a switcher.

Each window in a split keeps its header with its app, pickers, **Move to new tab**, and **Close
window**. **Move to new tab** (also **Window › Move to new tab**, or dragging the header up onto the
tab bar) takes the window out of the split and places it as its own tab right after the tab it came
from. There is no maximize, minimize, or zoom.

From the command line, `window move` splits, unsplits, and moves windows:

```bash
# Put window B to the right of window A, in A's tab.
compozy window move --workspace <workspace-id> --revision <revision> --id <window-b> \
  --desktop <desktop-id> --target <window-a> --placement right
# Put window B along the whole left edge of a tab.
compozy window move --workspace <workspace-id> --revision <revision> --id <window-b> \
  --desktop <desktop-id> --tab <tab-id> --placement left
# Take window B out of its split into its own tab.
compozy window move --workspace <workspace-id> --revision <revision> --id <window-b> \
  --desktop <desktop-id> --placement tab
# Move a whole tab to another desktop.
compozy window move --workspace <workspace-id> --revision <revision> --id <window-id> \
  --desktop <other-desktop-id> --group
compozy layout resize --workspace <workspace-id> --revision <revision> --split <node-id> \
  --boundary 0 --delta 0.15
compozy layout balance --workspace <workspace-id> --revision <revision> --tab <tab-id>
```

Placements are `tab` (the default), `left`, `right`, `top`, `bottom`, `before` (same as `left`),
`after` (same as `right`), and `center` (same as `tab` next to `--target`). `compozy window swap`
exchanges two windows of the same tab.

`compozy layout arrange --arrangement` accepts `horizontal`, `vertical`, `grid`, or `main_stack`
and builds one split tab from the listed windows where the first one's tab was. Main and stack gives
the first listed window the main column and splits the rest vertically beside it. **Window ›
Arrange** (and **Arrange ▸** on a tab) gathers the focused window, the rest of its tab, and the
front window of every other tab on the desktop into one split tab: **Main and stack** (the focused
window takes the main column), **Columns** (all side by side), **Grid** (up to four), and
**Balance sizes** (equal splits in the tab).

## Launching apps from the dock

Clicking an icon in the left dock goes to that app's open window, or opens it as a new tab when it
has none (Sessions goes to your latest session). Hold a modifier to open another window of the app
instead:

| Gesture            | Opens                                              |
| ------------------ | -------------------------------------------------- |
| Click              | The open window, or a new tab                      |
| Option (⌥) + click | A new window split beside the focused one          |
| Shift (⇧) + click  | A new desktop, with the new window as its only tab |

Right-click an icon (or focus it and press Shift+F10) for every destination: **Open in new tab**,
**Open in split**, **Open in new desktop**, and **Go to tab** when the app already has a window. For
Sessions, these open the session list window, where you pick a session or start a new one. Enter and
Space on a focused icon act like a plain click.

## Upgrading from v0.6 layouts

CompozyOS v0.7.0 removed floating windows, minimize, zoom, separately snapped windows, and tabs
inside a pane. The first time it opens a workspace saved by an earlier version, it converts the
layout once:

- Tiled windows keep their splits and become tabs. Windows that shared one pane as tabs become
  adjacent tabs, the active one in place.
- Floating and minimized windows become tabs after the tiled ones.
- Windows snapped side by side become one split tab when they line up; otherwise each becomes its own
  tab.
- A zoomed window returns to the desktop it came from, as its own tab.
- Discarded: the positions and sizes of floating windows, island frames, the minimized and zoomed
  state, the spot a minimized or zoomed window would have returned to, the grouping of several tabs
  inside one pane, the pin of a window that ends up inside a split (a pinned window that becomes its
  own tab stays pinned), the desktops that zoom created, and undo/redo history. No window, route,
  navigation history, or desktop is lost.

The app then shows **Your windows are now tabs** with the number of floating and minimized windows
that became tabs. Dismissing it in one window dismisses it everywhere. If the conversion fails, the
app shows **We could not move your layout to tabs**: your previous layout is kept, the desktop starts
with one New tab window, and **Retry** runs the conversion again; **Dismiss** hides the notice and keeps
the saved layout. In the app a retry is refused when you have changed the layout since the failure,
so your new work is never replaced; `compozy layout migration retry --replace` is the way to replace
it on purpose.

The same status is available to scripts and agents:

```bash
compozy layout migration status --workspace <workspace-id> -o json
compozy layout migration ack --workspace <workspace-id>
compozy layout migration retry --workspace <workspace-id>            # refused if the layout changed
compozy layout migration retry --workspace <workspace-id> --replace  # replace the current layout
```

`status` reports `state` (`none`, `migrated`, or `failed`), `from_version`, `acknowledged`, and a
`summary` with `desktops`, `tabs`, `windows`, `floating_to_tabs`, `minimized_to_tabs`,
`islands_merged`, `pins_dropped`, and `zoom_desktops_merged`. A failed status adds `error` (its
`code` is the converter's diagnostic code, or `migration.conversion_failed`) and
`failure_revision`; a successful retry clears both. When an upgrade has set earlier saved copies
aside (see the note below), `error.message` also says "<n> earlier layout backup(s) were set aside
and preserved; retry uses the current legacy backup." On a status with no conversion error, that
note is the `error` itself, with `code` `migration.backup_superseded`.
`compozy layout get` and `compozy__layout_get` include it as `migration` until it is acknowledged.

<OperatorNote>
  Do not downgrade to v0.6 after upgrading. v0.6 cannot read the converted layout and replaces it
  with a default desktop. The original v0.6 layout stays preserved inside the workspace state, but
  v0.6 does not restore it. Upgrading again converts the layout you used on v0.6, even when the
  first conversion failed. Nothing stored is lost: when the saved copy differs, the earlier copy is
  set aside unchanged in the same write, and **Retry**, **Dismiss**, and `compozy layout migration
  retry [--replace]` act on the newest saved copy. Copies set aside this way are never removed
  automatically; they are deleted only with their workspace or profile.

A layout saved by a newer CompozyOS (layout version 7 or later) is left untouched: that
workspace's layout answers `window_manager_unavailable` until you run the newer version again,
while CompozyOS starts, logs the skipped workspace (`window_manager.partition_reconciliation_skipped`),
and serves every other workspace.

</OperatorNote>

## Persistent desktops

```bash
compozy desktop list --workspace <workspace-id> -o json
compozy desktop clients register --workspace <workspace-id> --client <stable-client-id>
compozy desktop switch --workspace <workspace-id> --revision <revision> \
  --client <stable-client-id> --id <desktop-id>
compozy desktop delete --workspace <workspace-id> --revision <revision> --id <desktop-id> \
  --destination <desktop-id>
```

Deleting the final desktop is rejected. A desktop with tabs requires a distinct destination so the tab
transfer and deletion happen in one transaction. A desktop whose only tabs are New tab placeholders
counts as empty: it is deleted without `--destination`, and the placeholders are dropped, not moved.

### Desktops in the Web shell

The top bar shows one dot per desktop, the active desktop as a wider pill and an amber dot for a
desktop you are not on that needs you. Click a dot to switch to that desktop; the arrow keys move
between dots and the `desktop.switch.1`–`9`, next and previous shortcuts keep working. Past seven
desktops the bar shows five around the active one, and an overflow control on either side opens the
desktops overview at the hidden desktops.

Right-click a dot, or focus it and press Shift+F10 or the menu key, for **Rename**, **Move left**,
**Move right**, **Close desktop** and **New desktop**. Move left is absent on the first desktop,
Move right on the last, and Close desktop on the last remaining one. Rename and Close desktop open
the overview on that desktop's card, where you type the new name, or choose where its tabs go and
confirm. A desktop that holds only blank New tab tabs closes with a plain confirm and no destination.

**All desktops** in the top bar, or **Window › All desktops**, opens the overview over the work
area. Each card shows the desktop's layout, its name and tab count, and its first four tabs with a
count of the rest. Click the layout to switch to the desktop, or click a tab to jump to it; either
closes the overview. A card's pencil renames it, its context menu has **Move left**, **Move right**
and **Move a tab ▸**, and dragging a card to another position reorders the desktops. The bin on a
card closes that desktop in place: a desktop with tabs first asks which desktop receives them, and
only then offers the check that confirms. Escape cancels the close, then closes the overview.

To move a tab to another desktop, drag it from the tab bar onto that desktop's dot. While you drag,
the dots grow into labelled targets, and the tab moves with all its split windows. If the desktop is
hidden behind an overflow control, rest the tab on the control: the overview opens and takes the
drop on a card. You can also drag a tab row from one card to another inside the overview. A desktop
whose last tab leaves shows a New Tab window.

## Declarative layouts and recovery

Settings → Layouts accepts zero for the gap between split windows and for each outer inset independently.
A failed Save keeps your draft and offers retry or discard. The save result distinguishes applied
settings from saved settings that still need an action, and displays application warnings. If a save
reaches disk but application fails, retry applies the pending layout; discard keeps the configuration
already saved on disk.

`PATCH /api/settings/window-manager` retains the section fields and adds an `apply` receipt with
`applied`, `next_action`, `warnings`, and `partial_failures`. A successful HTTP response does not by
itself mean the configuration became active. Send `preserve_shortcuts: true` with a behavior-only
`config` to preserve the current shortcut and global-hotkey maps atomically. Explicit top-level
`shortcuts` or `global_shortcuts` still replace those maps; omitting the flag retains full-config
replacement behavior. Settings uses preservation so an open spacing draft cannot overwrite a
separately edited shortcut.

Semantic commands are the normal control surface. A validated layout document is the raw recovery
escape hatch:

```bash
compozy layout export --workspace <workspace-id> -o json > layout.json
compozy layout validate --workspace <workspace-id> --file layout.json -o json
compozy layout apply --workspace <workspace-id> --revision <revision> --file layout.json -o json
```

A layout document is `{version: 6, workspace_id, desktops, windows, overrides}`: the snapshot without
its revision, history, closed entries, and timestamps. Export always writes version 6 and omits
history. Version 4 and 5 documents from earlier releases are accepted everywhere a document is read
(`layout apply`, `layout validate`, `layout-profile put`, extension `window_layouts`, saved
profiles) and converted with the same rules as the [layout upgrade](#upgrading-from-v06-layouts);
saved profiles are rewritten to version 6 once at boot. Validate never writes. Apply validates the
complete document, binds it to the requested workspace, preserves current routes for surviving
window IDs, and replaces the topology atomically. Extensions can contribute declarative
`window_layout` resources; discover them through `compozy__resources_list`, then arrange by
`resource_id`. The Settings layout editor edits a profile as desktops, their tabs, and the splits
inside each tab, and lists and saves profiles through
`/api/workspaces/{workspace_id}/window-manager/layout-profiles`. That projection contains global
profiles plus profiles scoped to the selected workspace, and rejects cross-workspace writes.
Resources cannot execute code or receive pointer events.

### Retired apps in saved layouts

A saved layout can name an app that CompozyOS no longer ships. When the daemon loads a workspace's
saved window topology, it removes every window whose app is no longer registered, including the same
windows inside undo and redo history and recently closed entries. It then renormalizes the affected
desktops, rewrites a Settings window's saved `/settings/memory` route to `/settings`, and persists the
result once. After the write succeeds it logs `windowmanager.snapshot_reconciled` with the
`workspace_id`, the `profile_id`, the sorted `dropped_apps` (the IDs of the removed apps), the number
of `rewritten_routes`, and the new `revision`. The app IDs and the route count cover the current
windows, the undo and redo history, and the recently closed entries. The next load changes nothing.

Declarative `window_layout` resources follow the same rule. The daemon rewrites stored ones once at
boot, drops the removed windows from their participant slots, and logs
`window_manager.layout_reconciled` with the `resource_id`; layout listings always show the reconciled
form. A layout document passed to `compozy layout apply` carries `version` 6; version 4 and 5 documents are
still accepted and converted.

## All projects and User desktops

Besides one topology per project, each profile has two reserved desktops:

| Partition | Shown when                                                  | Address it with                                                               | Who may change it                                                |
| --------- | ----------------------------------------------------------- | ----------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| `global`  | The topbar globe is on ([All projects](/docs/all-projects)) | `/api/workspaces/global/window-manager`, `workspace: "global"` (native tools) | You only. Every agent is refused, including unrestricted ones.   |
| `user`    | **User** is focused ([User scope](/docs/user-scope))        | `--workspace @user`, `workspace: "@user"`                                     | You, and agents with the unrestricted grant of the same profile. |

A window remembers which data it shows through `route.search.workspace`: a project ID, `@user`, or
nothing. A remembered value always wins. Without one, a window on `global` shows every project, a
window on a project desktop shows that project, and a window on `user` shows User. On `global`, open,
navigate, reopen, and layout apply refuse a value that is neither `@user` nor a registered project
with `window_binding_invalid`. Saved layouts always load, even when a remembered project is gone.

When a session is deleted, every desktop of every profile drops it: its windows move to the empty
sessions view and it leaves closed-window, navigation, and undo history. When a project is removed,
windows bound to it fall back to their app's list, and nothing can bring the binding back.

## Agent and transport access

The lazy `compozy__window_manager` toolset registers 33 desktop, window, and layout tools — 28 current
and the 5 retired ones listed below — with structured
revisions, diagnostics, capability gates, and risk classifications. Resolve `compozy__tool_info` before
calling a tool. `compozy__window_move` splits (`placement` `left`, `right`, `top`, `bottom` with
`target_window_id` or `target_tab_id`), unsplits (`placement: "tab"`), and moves windows or whole tabs
(`move_group`) between desktops; `compozy__window_reorder`, `compozy__window_activate`, and
`compozy__window_pin` act on the window's tab; `compozy__layout_balance` takes `tab_id` or `split_id`.
CLI fallbacks are grouped under [`compozy desktop`](/docs/cli/desktop),
[`compozy window`](/docs/cli/window), and [`compozy layout`](/docs/cli/layout).

HTTP and UDS expose identical routes below
`/api/workspaces/{workspace_id}/window-manager`, including `GET` and `POST …/migration` for the
layout upgrade status; see the [Workspaces API](/docs/api/workspaces) for request and response
schemas. Command results report `changes` with `tab_ids`, `tab_split`, and `tab_unsplit`. The WebSocket
stream accepts an optional registered `client_id`. A bound stream fences that client's view in its
initial snapshot and then sends only strictly newer presentation frames for that ID alongside
workspace-revision topology events; an unbound stream receives topology only. After slow-consumer
eviction, reconnect and replace local state from the next fence. After a daemon restart, register the
same stable client ID again before reconnecting.

Use `compozy layout watch --workspace <workspace-id> --client <stable-client-id> -o jsonl` for the bound
CLI stream. Omit `--client` when only topology revisions are needed.

Committed operations emit these async hooks: `window_manager.layout.applied`,
`window_manager.desktop.created`, `window_manager.desktop.deleted`, `window_manager.window.moved`,
`window_manager.window.opened`, `window_manager.window.closed`, `window_manager.tab.split` (a tab went
from one window to several), `window_manager.tab.unsplit` (a tab went back to one window, or closed),
and `window_manager.tab.activated`. Pointer previews, navigation, focus changes, per-client tab flips,
and desktop switching do not emit extension hooks.

## Retired in v0.7.0

These surfaces still work until v0.8.0 so older scripts, agents, and configs keep loading, and are
deleted in v0.8.0. Retired commands, command IDs, and command fields answer with a `deprecations`
entry (`code`, `surface`, `replacement`, `removal_release: "v0.8.0"`, `message`), which the CLI
prints as one `warning:` line on stderr. Retired `config.toml` keys warn once when the configuration
