---
title: Governed Children
description: How call-created child sessions are bounded by lineage, idle TTL, caps, permission narrowing, and cleanup.
---

A governed child is a session a caller creates by calling an agent. The daemon owns every boundary
around it: lineage, idle TTL, depth and child caps, permission narrowing, and cleanup. The child
cannot outlive its parent, reach outside its lineage, or exceed its permissions.

[`compozy call`](/docs/agent-comms/calls) and `compozy__agent_call` are the only surfaces that
create one. This page documents the governance; the delegation contract itself lives in
[Agent comms](/docs/agent-comms).

Parent lineage is also used as informational creation provenance for some daemon-managed system
sessions, including Loop Goals. Those sessions can appear beneath their origin in session views,
but they do not inherit the origin's TTL, parent-stop behavior, or permission policy. Governed
children remain bound by their own lineage. Coordinator roots retain their daemon-owned TTL, caps,
and permission policy.

## Required constraints

| Constraint            | Behavior                                                                                                                        |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Valid parent identity | The caller must be a CompozyOS-managed session resolved from daemon-issued identity, or a resolved operator profile.            |
| Idle TTL              | Every child carries a parked-idle ceiling from `--idle-ttl` or `calls.idle_ttl`. The clock runs only while the child is parked. |
| Depth cap             | `calls.max_depth` (default `3`). At the wall the call tool is absent from the child's toolset.                                  |
| Child cap             | `calls.max_children` (default `5`) active children per parent. An over-cap call rejects; it never queues.                       |
| Concurrency budget    | `calls.max_active_per_root` (default `32`) per governed tree. Admitted work over it queues visibly.                             |
| Workspace and profile | A child stays inside its parent's profile and workspace. Cross-profile and cross-workspace targets are hard-denied.             |
| Permission subset     | Child tools, skills, MCP servers, workspace paths, network channels, and sandbox profiles must be a subset of the parent set.   |
| Unknown atoms         | Unknown child permission atoms count as widening and reject the call.                                                           |
| Parent stop           | A terminal parent drains its governed subtree; already-completed results are preserved.                                         |

The daemon rejects an invalid request with a typed error. It does not silently narrow a request and
continue. See [Budgets and safety](/docs/agent-comms/budgets-and-safety) for what each cap does when
it engages.

## Narrowing what a child may touch

Permission narrowing travels on the call, in its `narrow` object, and composes down the tree — a
grandchild cannot recover an atom its parent gave up. Widening is rejected with the offending atoms
named, and the subset check runs again after any `spawn.pre_create` hook patch, so a hook cannot
widen a child either.

Channel narrowing bounds which Compozy Network channels a child may use. It does not select Live
participation, create Network state, or make a child inherit its parent's participation — a
governed child stays Local unless it submits its own authorized participation request.

Workspace-path narrowing bounds which paths inside the workspace a child may touch. It is a
permission grant checked against the parent set, not a placement flag.

See [Narrow what a child may touch](/docs/agent-comms/subagents#narrow-what-a-child-may-touch).

## Feedback to the parent

When a managed session's call settles, CompozyOS queues a sanitized synthetic turn on that caller.
A successfully completed call with a stored `ResultRef` includes a bounded preview and the result
reference. Terminal failures and resultless terminal states carry their outcome and reason instead.
The wake never interrupts an active parent prompt, and it is suppressed when the parent is no longer
live or the delivery would wake the same session. Operator calls use `compozy call await` instead.

## Cleanup and active leases

The reaper wins over active leases. If idle-TTL expiry or parent-stop cleanup terminates a governed
child, CompozyOS first releases active task-run leases owned by that session with a structured
reason, then stops the child. Stale child claim tokens cannot complete or heartbeat recovered work.
Both paths retain the `spawn_reaper:` stop origin.

TTL cleanup checks the child runtime before classifying the stop: a child whose prompt already
settled with `done` or `end_turn` is reaped as completed, while a prompt still in flight is reaped
as a timeout.

## Hooks

Governed child creation exposes these hook events:

- `spawn.pre_create`
- `spawn.created`
- `spawn.parent_stopped`
- `spawn.ttl_expired`
- `spawn.reaped`

`spawn.pre_create` may deny or narrow a request, but hook patches cannot widen child permissions or
raise a TTL past its cap. The daemon enforces the permission subset after hook patches. The
call-level lifecycle has its own `call.*` events — see the
[Hook event catalog](/docs/hooks/event-catalog).
