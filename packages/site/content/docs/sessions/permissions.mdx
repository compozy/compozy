---
title: Permissions
description: How CompozyOS applies static permission modes, workspace boundaries, and interactive approvals during session execution.
---

CompozyOS applies permissions in two layers:

1. a daemon-side static policy for built-in ACP tool surfaces
2. an interactive approval flow for ACP `session/request_permission`

Both layers are scoped to the session workspace. `approve-all` by itself does not guarantee
unrestricted provider commands: the ACP provider also chooses an operating mode. Set
`permissions.provider_full_access = true` in the global config to request the provider's unrestricted mode for new
`approve-all` sessions, including Loop roles. CompozyOS selects `agent-full-access` for Codex,
`bypassPermissions` for Claude Code, `yolo` for Google Antigravity, and the `allow_all = on` option
for GitHub Copilot CLI. Copilot's Autopilot mode also approves everything, so it counts as an
unrestricted mode. Unsupported providers fail session resolution clearly instead
of silently accepting this preference. Existing mode selection is unchanged when the setting is
false. With the current Claude Code adapter, `approve-all` already selects `bypassPermissions`
when that mode is advertised. An agent can explicitly choose a narrower ACP mode, and stricter effective CompozyOS
permissions never permit an unrestricted mode. This setting does not bypass an outer CompozyOS
operating-system permissions; unrestricted provider commands run
with the daemon user's access within those boundaries.

When provider-native tool interception is active, CompozyOS may keep the upstream ACP session in an
approval-mediated mode so provider-native tool calls return through the CompozyOS execution gateway
before any real side effect. That does not change the configured policy outcome:
`approve-all` still auto-allows, `approve-reads` still auto-allows reads only, and `deny-all`
still auto-rejects at the execution boundary.

## Permission modes

CompozyOS supports five ordered permission levels:

| Level           | Backend behavior                                                                                                                                                              | Cross-workspace requests                                 |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| `deny-all`      | No automatic tool approvals; rejects ACP permission requests.                                                                                                                 | Denied without a prompt.                                 |
| `approve-reads` | Reads are allowed; edits and commands require approval.                                                                                                                       | Asks at the native-tool boundary; other boundaries deny. |
| `approve-edits` | Reads, workspace file edits and Compozy coordination tools are allowed; shell commands, destructive or open-world tools and changes to Compozy's own config require approval. | Same boundary as `approve-reads`.                        |
| `auto`          | Requests the provider's declared reviewer mode; CompozyOS keeps the `approve-edits` boundary.                                                                                 | Same boundary as `approve-reads`.                        |
| `approve-all`   | Automatically approves operations within the session's existing authority.                                                                                                    | Allowed without asking.                                  |

`auto` falls back to effective `approve-edits` with `permission_mode_degraded` when the reviewer is
undeclared, unavailable, or not selected by the adapter. It never falls back to full access.
Only trusted global provider configuration may declare `reviewer_mode`; workspace overlays cannot.
The provider catalog exposes this declaration for choosing a level.

### Choosing a level in the Web app

The Web app names the five levels the same way in every place it shows them: **Settings → General →
Permissions** for the global mode, the **Permissions** page of an agent (open the agent, then
**Permissions** under "How it's set up"), and the Advanced section of **New agent**.

| Value           | Label                   | What it means                                                                                  |
| --------------- | ----------------------- | ---------------------------------------------------------------------------------------------- |
| `deny-all`      | Ask before every action | Every action waits for your approval.                                                          |
| `approve-reads` | Ask before changes      | Reading is automatic. Changes and commands still ask.                                          |
| `approve-edits` | Edit on its own         | Edits files and runs its own coordination. Commands, deletions and settings changes still ask. |
| `auto`          | Let a reviewer decide   | The provider's AI reviewer approves routine work and stops risky actions.                      |
| `approve-all`   | Never ask               | Acts without asking. For agents you trust.                                                     |

An on-demand agent with no `permissions` shows **Follow Settings** and names the current Settings
level. A stays-on agent with no `permissions` shows **Edit on its own** marked Default. When the
agent's provider declares no reviewer, **Let a reviewer decide** is marked Not available and the page
says the agent uses Edit on its own instead. On Codex, **Never ask** explains that Codex keeps its own
reviewer unless full access is turned on separately.

The agent's Permissions page also holds two operator-only controls. **Whose requests can it answer?**
writes `session_approval` for stays-on agents: "Only its own sessions" (`children`) or "Any session it
can reach" (`workspace`). **Exceptions** writes `permission_rules`: up to 64 rows of action, a path
inside the project, and Allow or Never (`deny`). Exceptions apply only when the provider asks first;
they can't see inside shell commands. An agent that comes from an extension shows the page read-only.

### Defaults and overrides

The current built-in default configuration is:

```toml
[permissions]
mode = "approve-all"
```

That global mode can be overridden by an agent definition.

A stays-on definition with no explicit level uses `approve-edits`; its read-only check uses
`approve-reads`. The built-in stays-on Orchestrator declares `permissions: auto`, which runs at
`approve-edits` on a provider without a reviewer. An on-demand session keeps the global default. Each child resolves its own
definition and global default. A `permission_mode` request can narrow that level, never raise it.

## Permission rules

An operator-authored definition may add up to 64 `permission_rules`. Each rule has `kind`, `path`,
or both, and `decision: allow` or `deny`. Paths are workspace-relative glob patterns checked after
canonical path resolution. Deny matches win; an allow approves this request once. Unmatched requests
use the selected level. A path rule never matches a request without paths, and no rule permits a path
outside the workspace or overrides `deny-all`. Deny path patterns match regardless of letter case;
allow patterns match exactly. Rules cover only requests a provider asks: approvals for CompozyOS's
own tools follow the level alone. Rules are fixed when the session starts and are not inherited from
a parent. Extension-authored rules are ignored.

## Approving another session

A stays-on lineage can answer permission and clarification requests only for its descendants.
An operator-authored `session_approval: workspace` grants approval authority over sessions it can
already reach; it adds no workspace access. The effective grant is fixed at session start.
Extension-authored grants are ignored. Agents cannot edit these grants or set persistent tool approval
grants. Expired approvals remain denied, produce an `approval_expired` report, and notify the operator
unless muted. Repeating the same expired request is denied immediately until human engagement clears it.

## What the static policy actually covers

| Operation                                                 | `deny-all` | `approve-reads` | `approve-edits` | `auto`  | `approve-all` |
| --------------------------------------------------------- | ---------- | --------------- | --------------- | ------- | ------------- |
| Workspace read                                            | blocked    | allowed         | allowed         | allowed | allowed       |
| Workspace file edit                                       | blocked    | asks            | allowed         | allowed | allowed       |
| Terminal command                                          | blocked    | asks            | asks            | asks    | allowed       |
| CompozyOS coordination tool                               | asks       | asks            | allowed         | allowed | allowed       |
| Destructive, open-world or config-changing CompozyOS tool | asks       | asks            | asks            | asks    | allowed       |

At `approve-edits` and `auto`, an edit is allowed only when the request names at least one file inside
the workspace; an edit without file locations, and a request of kind `other` or with no kind, asks.

CompozyOS's own tools are decided once, by the risk each built-in tool declares. At `approve-edits`
and `auto`, a built-in tool that changes CompozyOS coordination state runs without asking: monitors,
child sessions, worktrees and their bindings, session names and links, tasks, Loops, Automations and
layouts. These still ask:

- destructive tools, such as removing a worktree, stopping or archiving a session, or deleting
  anything;
- open-world tools, and terminal commands or input;
- tools that change what an agent may do: config, tool approvals, hooks, extensions, agent
  definitions and persistent agents, reparenting sessions, and answering another session's prompts
  (a stays-on lineage still answers its own descendants).

Extension and MCP tools ask unless they are read-only. The provider's own permission request for a
CompozyOS tool does not prompt a second time: the daemon recognizes its hosted tool server from the
provider's server identity, not from the tool title, and an approval at one step covers the same call
at the other.

Workspace and tool restrictions remain in force after a level or rule permits a request.

## Workspace boundaries

Every permission decision is evaluated relative to the session workspace root.

CompozyOS resolves paths carefully:

- absolute paths are checked directly
- relative paths are resolved under the workspace root
- existing paths are resolved through symlinks
- missing paths are resolved through the first existing ancestor

If the final path escapes the workspace root, CompozyOS rejects it with a path-outside-workspace error.

## Cross-workspace access

A session belongs to one scope: a workspace, or the [User scope](/docs/user-scope) of its profile.
When an agent asks for a different one — a native tool call that names another `workspace` (or
`@user` from a project), an agent identity lookup, a task claim, a spawn, or a workspace
coordination command — the daemon sends that request through a single policy. The same workspace
under another profile counts as a different scope too. Unless the agent holds the
[unrestricted grant](#the-unrestricted-grant), the session's own permission mode decides it:

| Session mode                             | Cross-workspace outcome                                                                        |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `approve-all`                            | Allowed. The session crosses without being asked.                                              |
| `approve-reads`, `approve-edits`, `auto` | Asks at the native-tool boundary when the session is running; every other boundary denies.     |
| `deny-all`                               | Denied at every boundary, including the native-tool one. CompozyOS never prompts for crossing. |

The same table covers reading another profile (`profile`, `all_profiles`) and the
[All projects](/docs/all-projects) aggregates, so an `approve-all` session reads sessions in any
workspace, the User scope, and any profile, as you would. Changing another profile, or writing
through an aggregate route, still needs the [unrestricted grant](#the-unrestricted-grant).

A session tool called with only a `session_id`, such as `compozy__session_status`, is checked
against the workspace and profile of that session, not the caller's. You don't need to pass
`workspace` to read a session somewhere else.

### Redaction outside the agent's own scope

When an agent reads something outside its own workspace or profile, CompozyOS redacts secrets in
what comes back: session names, messages, tool inputs and outputs, and previews. It replaces
credential-shaped text with `[REDACTED]`: authorization headers and bearer tokens, `key=value` pairs
whose key names a secret, well-known provider key prefixes, URL passwords, and long random-looking
tokens. Redaction works by recognizing patterns, so a secret with no recognizable shape can still
come through. Reads inside the agent's own workspace and profile are not changed.

Operators are not governed by this policy — it applies to agent sessions. Extensions, automation,
and the daemon itself keep the behavior they have today; a permissive mode never
widens them.

`deny-all` reads differently on each axis, and that is deliberate. For tool risk it means "auto-allow
nothing, ask instead". For the workspace boundary it means "never cross, never ask". `deny-all` is
the lockdown setting for a session that must stay inside its own workspace.

The trade-off is that one mode now governs both axes. An `approve-all` session is open on tools and
open across workspaces; there is no separate setting for permissive tools with an isolated
workspace. The built-in default is `approve-all`, so set `[permissions] mode` — or the agent's
`permissions` field — to `approve-reads` or `deny-all` when a session should stay in its workspace.

### Denials

A denied request keeps the error shape it has today. Native tool denials carry the
`workspace_access_denied` reason code, and the message says which setting denied the call and what
would allow it: `deny-all`, an `approve-reads` request nobody answered, a rejected request, or a
write to another profile that needs the unrestricted grant. The message never names the target, so
a session that is denied gets the same answer whether the session it asked for exists or not. Other
boundaries keep this hint:

```text
cross-workspace access is denied by this session's permission mode; ask the operator to set the agent's permissions.mode to approve-all, or approve the prompt when asked
```

### The cross-workspace prompt

In `approve-reads`, `approve-edits` or `auto`, a cross-workspace native tool call from a running session becomes a pending
permission request instead of an immediate denial. CompozyOS computes the option set:

| Option ID        | Label                   | Effect                                                                           |
| ---------------- | ----------------------- | -------------------------------------------------------------------------------- |
| `allow_once`     | Allow once              | Allows this request only. The next crossing asks again.                          |
| `allow_session`  | Allow for this session  | Allows this request and every later crossing by that session, at every boundary. |
| `reject_once`    | Reject once             | Denies this request only. The next crossing asks again.                          |
| `reject_session` | Reject for this session | Denies this request and every later crossing by that session, at every boundary. |

Answer it like any other pending permission — the approvals bell in Web, `compozy session approve`,
or the approve route. The `allow-once`, `allow-always`, `reject-once`, and `reject-always` decisions
map onto the four options above in that order. The wait is bounded by
`[tools.policy] approval_timeout_seconds`; a timeout, a transport failure, or an answer outside the
option set denies the request and stores no session answer.

Crossings at every other boundary are denied outright in `approve-reads` — they never raise a
prompt. Once a session has answered `allow_session`, those boundaries start allowing.

### Session answers do not outlive the session

`allow_session` and `reject_session` are held in daemon memory, keyed by session ID. They apply to
every boundary for the rest of that session and disappear when the session stops or the daemon
restarts. Nothing is written to disk, and there is no list or revoke surface: stopping the session is
how you clear the answer. Persisted audit events show how later policy evaluations were decided.

### The unrestricted grant

An agent definition with `workspace_access: unrestricted` skips this table: its sessions reach every
workspace, the User scope, and every profile without a prompt, for reads and writes, and can read
[All projects](/docs/all-projects) aggregates whatever their permission mode. Only you can set the field, and it does not loosen tool
approvals — the permission mode still decides risky tools. Each allowed crossing is audited with
decision source `agent_grant`. See
[Give an agent access to everything](/docs/user-scope/unrestricted-agents).

### Audit

Each policy evaluation attempts a best-effort audit append — `workspace.access_granted` for an allow
or `workspace.access_denied` for a deny, including a prompt-eligible deny — scoped to the actor's own
workspace. The payload carries the actor and target profiles, the target kind (`workspace`, `user`,
`aggregate`, or `unresolved` for a session id that matches no session), the target workspace, boundary, decision source, and resolved mode.
An audit write failure is logged and does not change the access decision. Read persisted events with
`compozy logs --type <event-type>` or `GET /api/logs`.

See [Workspace Resolver](/docs/workspaces/resolver#isolation-and-cross-workspace-access) for
what workspace isolation covers today and what it does not.

## Interactive approval flow

Agents can also ask for permission explicitly with ACP `session/request_permission`.

That flow behaves like this:

1. the agent sends a permission request with one or more offered outcomes
2. CompozyOS checks the workspace boundary first
3. CompozyOS either auto-selects an outcome or records a pending permission event
4. a client approves or rejects it
5. CompozyOS returns the selected ACP outcome to the agent

### Auto decisions vs pending decisions

| Session mode    | Request kind                   | Immediate result |
| --------------- | ------------------------------ | ---------------- |
| `approve-all`   | any valid in-workspace request | `allow-once`     |
| `approve-reads` | ACP read request               | `allow-once`     |
| `approve-reads` | non-read ACP request           | pending approval |
| `deny-all`      | any ACP request                | `reject-once`    |

Outside-workspace requests are rejected immediately instead of becoming pending.

### Decisions clients can send

The approval request body accepts these decisions:

- `allow-once`
- `allow-always`
- `reject-once`
- `reject-always`

Example HTTP approval:

```bash
curl -X POST http://localhost:2123/api/workspaces/ws_alpha/sessions/sess-1234/approve \
  -H "Content-Type: application/json" \
  -d '{
    "request_id": "req-42",
    "turn_id": "turn-9abc",
    "decision": "allow-always"
  }'
```

Success response:

```json
{
  "status": "approved"
}
```

### Approval timeout

Pending interactive permission requests wait up to 5 minutes by default. If no approval arrives,
CompozyOS resolves the request as `reject-once`.

### What `allow-always` and `reject-always` mean

For a generic ACP permission request, CompozyOS picks the closest option offered by the agent and returns
it. The agent runtime owns the long-lived meaning of "always" for that request.

Native tools routed through CompozyOS's approval gateway have an additional daemon-owned contract.
Selecting `allow-always` or `reject-always` stores an exact workspace + agent + tool + input-digest
decision. The next matching invocation uses that decision before prompting, and the decision
survives daemon restart. Operators and agents can inspect or revoke these records through Web,
`compozy tool approvals`, HTTP/UDS, or the `compozy__tool_approvals_*` native tools. This does not change ACP
subprocess permissions or operating-system policy. See [Policy and Invocation](/docs/tools/policy-and-invocation#remembered-native-tool-decisions).

## Permission events

Permission requests and resolutions are visible in both prompt streams and persisted session
history.

Example canonical permission payload:

```json
{
  "schema": "compozy.session.event.v1",
  "type": "permission",
  "session_id": "acp-session-77",
  "turn_id": "turn-9abc",
  "request_id": "req-42",
  "timestamp": "2026-04-16T01:22:00Z",
  "action": "session/request_permission",
  "resource": "/absolute/path/to/repo/internal/session/manager.go",
  "decision": "allow-always",
  "title": "Write file",
  "tool_call_id": "tool-call-7",
  "raw": {
    "tool_call": {
      "kind": "edit",
      "title": "Write file"
    }
  }
}
```

If a request is still pending, the initial permission event is recorded with no final `decision`
yet. The resolved decision appears when approval completes.

## Current transport status

Interactive approval is exposed differently across CompozyOS transports today:

| Transport | Status                                                                           |
| --------- | -------------------------------------------------------------------------------- |
| HTTP      | implemented at `POST /api/workspaces/:workspace_id/sessions/:session_id/approve` |
| UDS       | implemented at `POST /api/workspaces/:workspace_id/sessions/:session_id/approve` |
| CLI       | implemented at `compozy session approve <id>`                                    |

That means browser-facing clients, UDS clients, and the local CLI all drive the same approval
surface today. [Cross-workspace prompts](#the-prompt-in-approve-reads) arrive through that same
surface. They add no route, command, or Settings section of their own, and a session-scoped answer
has no management surface at all.

## Clarification questions are not approvals

`compozy__clarify` lets an active managed session ask one question and wait for an operator
(unbounded unless `[tools.clarify] timeout` is finite). It is a read-only, non-destructive tool with its own live broker; it does not reuse permission
requests, approval decisions, or remembered native-tool grants. One session can have at most one
pending clarification.

The question may offer up to four unique choices or accept free text. The HTTP/UDS wire uses a
zero-based `choice_index`; the CLI presents one-based choice numbers:

```bash
compozy session clarify pending <session-id> -o json
compozy session clarify answer <session-id> <request-id> --choice 1 -o json
compozy session clarify answer <session-id> <request-id> --text "Use staging" -o json
```

HTTP and UDS use the same workspace-scoped routes:

- `GET /api/workspaces/:workspace_id/sessions/:session_id/clarifications`
- `POST /api/workspaces/:workspace_id/sessions/:session_id/clarifications/:request_id/answer`

The live pending list is exact daemon truth. Durable `clarify` events preserve the pending,
resolved, timed-out, and canceled transitions for timeline and audit. Under a finite `[tools.clarify]
timeout`, expiry returns exactly
`{"choice":null,"text":"","fallback":true}`; stopping the session or daemon cancels the wait.

## Practical configuration example

Global default in `~/.compozy/config.toml`:

```toml
[permissions]
mode = "approve-reads"
```

Per-agent override in an `AGENT.md` definition:

```text
---
name: reviewer
provider: codex
permissions: deny-all
---

Review code changes and explain the risk.
```

Use the global default for the team baseline, then override individual agents only when they need a
different safety envelope. There is no `compozy session new --permissions` flag today, and the session
create HTTP payload does not currently accept a permissions override either.
