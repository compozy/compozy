title: Gateway quickstart
description: Reach CompozyOS from your phone or laptop over a trusted LAN or private Tailscale network — enable access, pair a device, and open the web UI.
---

Choose the network path that matches your deployment:

- **Trusted LAN:** the HTTP listener binds to a local network interface. Traffic stays on that network;
  no external relay or internet traffic is required. This is suitable for an isolated network or a DMZ
  with firewall rules that restrict the allowed source addresses. Continue with [Local network access](#local-network-access).
- **Private Tailscale network:** the gateway keeps its listeners on loopback and uses the bundled
  Tailscale provider to carry traffic over your tailnet. Continue with [Tailscale private overlay](#tailscale-private-overlay).

## Local network access

Use this path when the browser and daemon are on the same trusted network. The HTTP listener is the
reachable surface; the Gateway device credential still protects the UI and API after pairing.

Set the global gateway ceiling and the HTTP listener configuration:

```bash
compozy config set gateway.enabled true
```

Edit the global `$COMPOZY_HOME/config.toml`:

```toml
[http]
host = "0.0.0.0"
allow_remote_access = true
allowed_ips = ["192.168.1.0/24"]
```

Replace the CIDR range with the network that should reach the daemon. An empty `allowed_ips` list
allows any reachable source, so use an explicit range when the host has more than one network or is
placed in a DMZ. Restart the daemon after changing the HTTP bind settings.

On the daemon machine, create a short-lived pairing artifact:

```bash
compozy pair mint
```

Move the private artifact to the browser machine through a trusted channel, open
`http://<daemon-lan-address>:2123`, and enter the code at the pairing gate. The redeem request is
the only unauthenticated bootstrap route; after it succeeds, the browser receives its device
credential and all other remote requests require that credential. Pairing codes are single-use and
expire after five minutes by default.

This flow does not enable a Tailscale provider, public gateway surface, or external relay. Keep the
LAN itself trusted and enforce the intended boundary with host and network firewalls.

## Tailscale private overlay

The steps below use the bundled Tailscale provider. At the end of this flow you will have one address,
`https://compozy-gateway.<your-tailnet>.ts.net:8443`, that opens the full CompozyOS web UI from your
phone or laptop over your own private Tailscale network. Nothing becomes reachable from the public internet.

Expect about ten minutes, most of it waiting for the first certificate.

## Before you start

- The CompozyOS daemon is running on this machine (`compozy status`).
- You have a [Tailscale](https://tailscale.com) account. The free plan is enough.
- In the Tailscale admin console, **MagicDNS and HTTPS certificates are enabled** for your tailnet
  (under **DNS**). The gateway serves HTTPS and cannot start without a certificate domain.
- The device you want to pair has the Tailscale app installed and is signed into the **same
  tailnet**. The private address only resolves for members of your network.

## Step 1: Allow the gateway

`gateway.enabled` is a machine-wide ceiling — a hard maximum, not a switch that exposes anything by
itself. Raise it once:

```bash
compozy config set gateway.enabled true
```

The change applies live; no restart. If you skip this step, every later command refuses with:

```text
gateway exposure refused: gateway.enabled is false and blocks every remote transition; fix: set gateway.enabled=true, then retry the explicit transition
```

Every gateway refusal reads like that — it names its cause and the fix.

## Step 2: Give the Tailscale extension an auth key

In the Tailscale admin console, create an auth key under **Settings → Keys**. Then bind it — the
value is typed into a hidden prompt and never appears in your shell history, logs, or status output:

```bash
compozy extension secrets set tailscale --env TS_AUTHKEY
```

The Tailscale extension ships inside CompozyOS and uses your account only. There is nothing else to
install — details on the [Tailscale extension](/docs/gateway/tailscale) page.

## Step 3: Turn the extension on

```bash
compozy extension enable tailscale
```

The first enable refuses with a network requirement digest — the extension declares that it carries
gateway traffic, and CompozyOS asks you to confirm exactly that. The refusal prints the exact command
to run, in the shape:

```bash
compozy extension enable tailscale --confirm-network-requirement <digest>
```

Run it and the extension is on.

## Step 4: Activate the provider for the private tier

```bash
compozy gateway provider enable tailscale --tier private --source bundled
```

On a fresh gateway no `--generation` flag is needed. If a later change reports a
`gateway generation conflict`, read the current generation from `compozy gateway status -o json`
and retry with `--generation <n>` — see [Devices, audit, and teardown](/docs/gateway/manage#generation-conflicts).

## Step 5: Turn on the private surface

```bash
compozy gateway surface enable operator_ui --tier private
```

The daemon now binds a loopback listener, asks Tailscale to establish reachability, verifies the
endpoint with a one-time challenge, and only then advertises the address.

## Step 6: Wait for the address

```bash
compozy gateway status -o json
```

The human output shows summary counts; the JSON carries the proof. You are waiting for
`advertised: true` and a live address (output trimmed):

```json
{
  "tiers": [{ "tier": "private", "observed": "up", "advertised": true }],
  "providers": [{ "name": "tailscale", "tier": "private", "health": "healthy" }],
  "addresses": [
    {
      "tier": "private",
      "address": "https://compozy-gateway.<your-tailnet>.ts.net:8443",
      "live": true
    }
  ]
}
```

The first activation is the slow one: Tailscale issues an HTTPS certificate for the new
`compozy-gateway` node, which can take a minute. Until then status reports the provider as
establishing or degraded while the daemon retries on its own — that is a wait state, not a failure.
An address appears only after it is verified.

## Step 7: Pair your device

Reaching the address is not enough — every new device sees a pairing gate until you admit it.

The easiest path is the web UI: **Settings → Gateway → Pair a device** shows a one-time code as a
scannable QR and as copyable text. From the CLI:

```bash
compozy pair mint
```

```text
Pairing
  Artifact File  ~/.compozy/gateway/credentials/<file>
  Expires        2026-08-09T16:45:00Z
```

The pairing code is written to that private file, never to your terminal. On your phone, open
`https://compozy-gateway.<your-tailnet>.ts.net:8443`, enter the code at the pairing gate, and name
the device.

<OperatorNote>
  A pairing code is single-use and expires after five minutes by default. Move it through a channel
  you trust and delete the file after use. Pairing is only ever minted locally or over the private
  tier — the public address cannot mint or redeem a pairing under any configuration.
</OperatorNote>

## Step 8: Confirm it worked

On the phone you are now in the full web UI — same sessions, same state as on this machine. Back on
the daemon machine:

```bash
compozy device list
```

```text
Devices
  ID          NAME       KIND              ORIGIN   LAST SEEN              REVOKED
  dev_...     My phone   operator_device   local    2026-08-09T16:41:12Z   false
```

`KIND` distinguishes browser devices (`operator_device`) from CLI connection profiles
(`cli_profile`); `ORIGIN` records where the pairing was minted — `local` on this machine, `private`
over the private tier.

Done: your daemon is reachable from your devices, and only your devices.

## If it didn't work

| Symptom                                                        | Fix                                                                                                                                 |
| -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `gateway exposure refused: gateway.enabled is false…`          | Run step 1. The refusal text always names the fix.                                                                                  |
| `TS_AUTHKEY binding is required`                               | Run step 2. Expired or revoked keys fail the same way — mint a new key and bind it again.                                           |
| `tailscale: tailnet HTTPS certificate domain is unavailable`   | Enable MagicDNS and HTTPS certificates in the Tailscale admin console under **DNS**, then retry.                                    |
| Status shows `establishing` or a degraded provider for minutes | First activation issues a certificate; the daemon retries with backoff. Recheck `compozy gateway status -o json` after a minute.    |
| The phone cannot open the address                              | Confirm the phone runs Tailscale and is signed into the same tailnet, then re-check the address in `addresses[]` with `live: true`. |
| The pairing code is rejected                                   | Codes are single-use and expire in five minutes. Mint a fresh one.                                                                  |

Still stuck? The [Tailscale extension](/docs/gateway/tailscale#troubleshooting) page covers
provider-side failures in more detail.
